Don't Build What Didn't Change: Scheduling a Build System Past 400,000 Builds a Month

September 2026 · 20 min read

For two and a half years I worked on an in-house CI system: thousands of repositories, tens of thousands of buildable modules, a dependency graph that crossed repository boundaries, and a build volume that went from roughly 80,000 builds a month to over 400,000 while I was there. I ended up tech lead of the team that owned it.

The interesting problem in a system like that is not "how do I run a build". Running a build is a container and a command. The interesting problem is deciding what to build, in what order, and — far more valuable — what not to build at all, while the answer keeps changing underneath you because people keep pushing commits.

This post is about the scheduling side of that system: the model, the optimization that removed the most work, the race conditions that model created, and the things I got wrong. I have anonymized it — no company, no service names, no links. The mechanics are what matter, and they generalize to any CI system that outgrew its original assumptions.

The Model: Repo, Branch, Module, and the Graph Between Them

Four entities carry the whole design.

EntityWhat it isWhy it exists separately
BranchA repository branch the system tracksBuild state is per branch, not per repo
ModuleOne buildable unit inside a branch — a Maven module, a frontend package, a Docker imageA repo with 40 modules should not rebuild 40 things because one changed
Repo buildOne triggered run over a branch: discover modules, then build the affected onesIt is the unit a human recognizes
Inter-project buildThe transitive closure of downstream modules in other repositories that depend on what was just builtThis is the part that makes it a distributed scheduling problem instead of a queue

The last one is the whole game. In a company with thousands of repositories and a shared artifact tree, a merge to a widely-used library is not one build. It is a wavefront: the library builds, then everything that depends on it builds, then everything that depends on those builds, level by level, until the graph is exhausted. A single commit to a parent POM could schedule thousands of module builds.

Each inter-project build stores a mapping row per downstream module and a topological sort of the graph. As module builds finish, the scheduler walks the sort, launches what is now unblocked, and marks the inter-project build complete when every mapping reaches a terminal state. That data structure is the reason for most of what follows — the optimizations, the watchdog, and the bugs.

Why the Wavefront Exists: Everything Is a Snapshot

None of the above makes sense without the strategy underneath it, which I should have stated first: every module published a snapshot on every build, and consumers depended on the latest snapshot rather than on a pinned release.

There is no dependency-upgrade ritual in that world. Nobody opens a pull request bumping a library from 4.2.1 to 4.3.0, nobody maintains a renovation bot, nobody discovers at release time that the version they pinned eleven months ago has a known vulnerability. Downstream always has the newest upstream, by construction.

The price is that a library change is immediately everyone's problem. Pinning is a buffer: it lets a breaking change sit harmlessly in a registry until each consumer chooses to walk into it, one team at a time, usually months later, when the author has forgotten the context and the person doing the upgrade has none. Remove the buffer and the failure surfaces at once — which is better, but only if somebody actually runs the downstream tests.

That is what inter-project builds are for. They are not a scheduling nicety and not an optimization. They are the mechanism that makes unpinned snapshots safe:

  • A merge to a library propagates immediately into every module that depends on it, transitively, level by level.
  • Each of those modules runs its own tests against the new artifact within minutes, not at some future upgrade.
  • The result comes back to the author of the change, while they still have the change in their head. The person who broke a downstream consumer learns it from their own merge, not from that team's sprint three months later.
  • Production ends up running the freshest version of everything, so a fix — a bug, a security patch, a performance regression — reaches every consumer as fast as the graph can be walked, with no migration campaign and no coordination meeting.
Continuous integration, taken literally: integration happens continuously, against the tip of everything, instead of being deferred to whenever each consumer feels like it. The build volume is what that costs.

That last sentence reframes the whole system. Four hundred thousand builds a month is not a symptom of inefficiency — a large part of it is the deliberate price of never having a stale dependency anywhere in the company. Which means the scheduling work has two jobs that pull against each other:

GoalWhy it matters hereWhat it pushes you toward
Propagate fastFreshness and fast feedback are the entire point; a wavefront that takes hours is a buffer reintroduced by accidentAggressive scheduling, pre-provisioned capacity, low queue latency
Do not build what cannot have changedThe graph is transitive and wide; naive propagation rebuilds half the company for a comment fixProvable skips, consolidation, change-based graph construction

Every decision in the rest of this post sits somewhere on that line. And it explains a distinction that is otherwise easy to miss in what follows: the skip optimization applies to branch builds, where an upstream module can be proven identical to what the default branch already published. On the default branch itself, propagation is the product. You do not skip a downstream build there to save capacity, because the downstream test run against the new snapshot is the thing you are paying for.

Decision 1 — The Cheapest Build Is the One You Prove You Can Skip

The single largest reduction in build volume did not come from making builds faster. It came from establishing, cheaply and safely, that a build was unnecessary.

Here is the situation. You push to a feature branch. Your branch contains twelve modules; you changed one. But that one depends on three upstream modules in the same branch, and the naive scheduler rebuilds all four, because on a branch there are no published artifacts for the upstream three — they exist only on the default branch.

The optimization: for each upstream module, find the best common ancestor commit between the branch and the default branch. If the module was already built successfully at that commit, and nothing in the module changed on the branch since, then the artifact built at that commit is exactly the artifact the branch would produce. Don't rebuild it. Reuse its resolved version.

That last phrase is where the work is. Branch builds publish artifacts under munged versions — a version string derived from the branch, so branch artifacts never collide with default-branch artifacts. To skip an upstream build, you must hand the downstream build the exact resolved version of the artifact you are reusing. So:

  • Every module build stores its resolved version in a column of its own, rather than being re-derived later from somewhere else.
  • A build plugin emits a metadata file with resolved versions, so the information survives outside the build system's own database.
  • The scheduler passes an overrides map into the build as an environment variable; the version-setting script parses it and rewrites the dependency versions before the build starts.

Then the edge cases, each of which is a real class of bug:

CaseWhat goes wrong naivelyResolution
Module was never built at the common ancestorNo version to reuse; either rebuild or failWalk back for the nearest successful build and reuse that, once proven safe
Branch is behind its default branchYou reuse an artifact newer than the branch expectsOnly apply the optimization when the branch is not behind; otherwise reuse the previous build's own override map
Brand-new branchNo build history at all on the branchTreat the divergence point as the ancestor
Dependency declared explicitly in the configThe human wrote it down for a reason the graph does not knowExclude explicit declarations from the optimization

And the rollout: repository allowlist, then percentage, then default-on, with a kill switch at every stage. An optimization that skips builds is, from a user's point of view, indistinguishable from a build system that silently lost their code. You roll that out slowly or you lose trust you cannot buy back.

The principle

Caching build outputs is a well-trodden problem. Caching the decision not to build is a different one: it requires you to prove equivalence between two commits, and to carry the identity of the artifact you are substituting all the way down the graph. If you cannot name the exact version you are reusing, you are not skipping a build — you are guessing.

Decision 2 — The Graph Needs a Watchdog, Because Events Lie

The wavefront advances on events: a module build finished, therefore look at its downstream mappings. Events get lost. Processes get killed mid-transaction. A module gets deleted from a repository while an inter-project build that references it is still in flight. Every one of those leaves an inter-project build that will never complete, which means a pull request that never goes green, which means a support ticket.

We added a scheduled reconciler over active inter-project builds. Not a retry of the event — a reconciliation of the state:

  • An inter-project build with no topological sort can never progress. Fail it explicitly rather than leaving it pending forever.
  • If every mapping is terminal but the parent is not marked complete, mark it complete. The event that would have done this is gone.
  • If a mapping points at a module that no longer exists, resolve it rather than blocking on a row that can never move.
  • If a module became unreachable because an upstream failed, mark it unreachable instead of leaving it "in progress".

This is the same lesson I keep re-learning in distributed systems, and I wrote about the same shape in an IoT context: event-driven progress needs a state-driven backstop. The events are the fast path. The reconciler is the correctness path. If the only way your system reaches a terminal state is an event arriving, then your system's liveness is exactly as good as your message delivery, which is worse than you think.

Decision 3 — Consolidation, and the Race It Creates

Consolidation is the optimization where two pending builds for the same branch collapse into one: if three commits land in ten seconds, build once at the tip, not three times. It is obviously correct and it is worth an enormous amount of capacity.

It is also where the nastiest races lived, because a build is not atomic. A repo build goes through a discovering modules phase before it knows what to build. Consolidating a new push into a build that is already discovering means the discovery may have already read the tree — at a commit that does not include the new push. The result is the worst possible outcome in CI: a build that reports success for a commit it never built.

We fixed specific instances of it twice — ensuring entities were re-read before recomputing commit info, handling the ordering explicitly — and both fixes held, and both left the same uneasy feeling: the invariant was now maintained by careful reasoning in several places rather than by construction.

So the third fix was to stop being clever: never consolidate a push build into a build that is already discovering. Enqueue a new build instead. It costs a little capacity in a narrow window, and it removes an entire category of race and the locking scheme that would have been needed to close it properly.

Given a choice between a correct invariant enforced by locking and a slightly wasteful invariant enforced by construction, take the second one every time in a system where the failure mode is "we told you it passed and it didn't".

A related one: when a push build and a dependency build merge, what downstream work should be scheduled? The intuitive answer — the union of what each would have scheduled — over-schedules badly. The right answer is to build the inter-project graph from what changed, not from what is about to be built. Those are different sets, and the second one grows every time a build gets consolidated into another.

The Scar — A Batch Insert That Changed the Failure Mode

Large inter-project builds insert a lot of mapping rows — one per downstream module, and a parent POM change can mean thousands. Those inserts were happening one at a time. Batching them is a textbook fix, it measured beautifully, and we shipped it.

Scar

The batch path did not handle one case the row-at-a-time path did: mappings for cancelled builds were not always inserted. The rows were missing, so the graph walk had holes, so a fraction of inter-project builds could never reach a terminal state — they stayed in progress forever. A throughput change had quietly become a correctness change, and the symptom appeared far away from the cause, days later, in a state-machine that looked stuck for no reason. We reverted it in parts and came back to it with the cancellation path covered.

What I take from it: a batching change is not a performance change. It is a change to atomicity and ordering, and therefore to the failure modes. The review question is not "is this faster" — it obviously is — it is "which of the old path's implicit guarantees does the new one drop". Nobody asked that, including me.

Decision 4 — The Scheduler's Hot Path Is the Database, Always

Every scaling problem we had traced back to the relational store. The build system's database is a workload most teams never see: enormous write volume of short-lived state rows, plus a scheduler that reads the same slow-moving metadata thousands of times a second. The fixes, roughly in order of payoff:

  1. Cache the slow-moving reads. Tracing showed nearly all of the graph-walk time was spent fetching branch identifiers and module metadata — over and over, inside one execution. Bounded caches with an expiry measured in an hour removed most of it. The data changes on the timescale of a human editing a repository; the code was reading it at machine timescale.
  2. Delete the indexes that duplicate each other. One table carried a duplicate index on a column that already had one, plus a single-column index made redundant by a composite. Every one of those was write amplification on the highest-write table in the system, paid on every insert, forever.
  3. Stop streaming results you meant to page. Several data-access methods used a streaming result iterator and were effectively holding cursors while doing work. Replacing them with explicit keyset pagination made the memory profile predictable and unblocked a driver upgrade that had been stuck on exactly that pattern.
  4. Shrink the payload before you optimize the query. One widely-used read returned the full dependency graph and commit info inside every module state object. Almost no caller needed either. Removing them from the result was a bigger win than any index.
  5. Denormalize what you query in a loop. "The last successful build for this module" was an expensive query executed constantly. It became a column on the module, updated on completion.
  6. Do not compute metrics with queries. Active build counts were being produced by periodically querying the database. They became in-memory counters incremented by the code that causes the transition, produced by dedicated workers rather than by the scheduler, and the gauges that nobody had looked at in a year were deleted.
  7. Do not enqueue work you already know is a no-op. Skipped module builds were still being written to the queue, then read, then discarded. Not enqueueing them removed a meaningful share of daily queue inserts.

Also: keep QA and production schemas aligned, deliberately, as a chore. A long series of unglamorous migrations dropping tables that existed only in one environment and adding indexes missing from the other. Every environment divergence is a future incident where the thing you tested is not the thing you shipped.

Decision 5 — A Queue That Survives Its Own Consumers

The event queue in front of the scheduler needed three properties that its original design did not have.

Failures must be recoverable. A poison event used to be simply lost. We added a table of failed queue items and a job that replays them with a retry cap. Not sophisticated; the point is that "we dropped it" stopped being the default outcome.

The payload should be minimal. Incoming webhook payloads carry a lot the scheduler will never read. A "lightener" strips them before enqueueing. Less to store, less to deserialize, fewer schema-drift surprises.

Deserialization must not be coupled to a schema you don't control. Queue items were being deserialized into typed objects at read time, which meant any upstream model change turned into a wave of unreadable items sitting in the queue. Storing and reading them as opaque strings, then parsing at the point of use, made the queue resilient to schema changes by construction. After one incident caused by exactly this, we also introduced our own internal models for the provider's push and delete events, rather than consuming the vendor's model directly — and removed the migration shim once it was done.

The general rule: a queue should be the dumbest component in the system. Every piece of intelligence you put in it becomes a way for it to reject your messages during an incident.

Decision 6 — Provision Capacity Against the Graph, Not the Queue

Build pods take time to start: pull the image, mount caches, warm the toolchain. If you only start a pod when a module build becomes runnable, every module in a dependency chain pays that startup serially.

But the scheduler knows the graph. It knows which modules are waiting for upstream builds, which means it knows with reasonable confidence what will become runnable in the next couple of minutes. So we provisioned a configurable percentage of those pods early, so the container is warm when the upstream finishes.

With one exclusion that is worth stating because it is the kind of detail that only comes from looking at real data: frontend modules were excluded, because in that repo layout they typically build together in the same container, so pre-provisioning for them bought nothing and consumed cluster capacity that the Java builds needed.

What This Cost, and What It Bought

Over that period the system went from roughly 80,000 to over 400,000 builds a month — a fivefold increase in load, most of it the deliberate cost of propagating every change to every consumer — while critical incidents went down and artifact storage costs went down with them. Almost none of that came from a single rewrite. It came from a long series of the changes above: skip what didn't change, reconcile what events lost, stop asking the database questions it has already answered, and choose invariants you can enforce by construction.

The uncomfortable part is how much of the work was subtraction. Unused jobs, dead configuration flags that had been false since a date two years earlier, a notification path nobody had read in a year, duplicate indexes, metrics no dashboard displayed. A build system accretes this faster than a product does, because nobody's roadmap has "delete the thing that works" on it — and every dead path is something an on-call engineer has to rule out at 3am before they can find the live one.

Key Takeaways

  1. Unpinned snapshots move the cost from upgrades to builds. No dependency-bump ritual, no stale library anywhere — paid for by propagating every change through the whole downstream graph immediately, which is what inter-project builds are.
  2. Feedback must reach the author, not the consumer. The value of propagating within minutes is that the person who broke something still remembers why they changed it.
  3. The best optimization is a provable skip. Establish equivalence with the default branch, reuse the exact resolved artifact version, and carry that identity all the way through the graph.
  4. Roll out anything that skips work behind an allowlist and a percentage. A wrongly-skipped build is indistinguishable from lost code.
  5. Event-driven progress needs a state-driven reconciler. If terminal states are only reachable via events, liveness equals delivery reliability.
  6. Prefer invariants enforced by construction over invariants enforced by locking. Refusing to consolidate into a discovering build removed a whole race class for a rounding error of capacity.
  7. Schedule downstream work from what changed, not from what will be built. Those sets diverge the moment builds consolidate.
  8. Batching is an atomicity change, not a speed change. Ask which implicit guarantee the old path had that the new one drops.
  9. Cache reads whose data changes at human speed. Metadata read thousands of times per second changes when someone edits a repository.
  10. Shrink payloads before tuning queries, and delete redundant indexes. Both are paid on every single operation.
  11. Never compute metrics with database queries. Counters at the transition, produced by a worker, not by the scheduler.
  12. Keep the queue dumb and its payloads opaque. Typed deserialization at read time turns an upstream schema change into an outage.
  13. Provision against the graph. The scheduler knows what is about to be runnable; start those containers early — except where the build layout makes it pointless.
  14. Budget for deletion. Dead flags and unused jobs are not free: they are the paths on-call has to eliminate before finding the real one.
