The Bugs I Couldn't See: Rewriting a Scraper in Scrapy

April 2026 · 16 min read

My first scraper worked. That was the problem. It ran, it finished, it filled the database with 848 recipes and 230 ingredients, and it never once told me that a fifth of some categories was missing, that ingredient names were losing the words wrapped in <strong>, or that monkfish had been filed under fruit. A scraper that crashes teaches you something. A scraper that quietly returns almost the right data teaches you nothing until you go looking.

I went looking while rewriting the whole thing in Scrapy for my food AI platform — a side project that started for fun and got interesting. This post is the argument for the framework, the five decisions that changed what ended up in the database, and the 84-test audit I ran to prove the new spiders produced the same data as the old scripts. Including the parts where they did not, which is the whole reason the audit existed.

Part 1 — The Two Scripts That Worked

The original setup was two standalone Python files: crawler.py (335 lines) and ingredient_crawler.py (548 lines). Each one used a requests.Session() with a spoofed Chrome User-Agent, hand-written exponential backoff, hardcoded time.sleep(0.5) between requests, and a single function per page that fetched the URL, parsed the HTML, extracted the fields, downloaded the image, wrote to the database and printed progress.

Nothing about that is unreasonable for the first version. It becomes unreasonable at the point where you want a second spider, or concurrency, or to run it on a schedule. Every improvement I wanted — parallel requests, a retry policy I could reason about, rate limiting that responds to the server instead of a guess, robots.txt compliance, resuming after a crash — was a component I would have to write, and each one has already been written better somewhere else.

Why not just add httpx?

This was the option I took seriously. httpx gives you async HTTP; parsel gives you CSS and XPath selectors, and it is literally the same selector library Scrapy uses. It looks like the lightweight answer. The problem is what sits between those two pieces.

Concurrency, error handling, rate limiting and robots.txt get solved one way or another. Doing them by hand means reimplementing a battle-tested framework, badly, in the margins of a project that is about food data. The things that genuinely required my knowledge — which selectors to trust, how to read a recipe page, how to classify an ingredient — are identical in both worlds. They just moved from standalone functions into spider methods.

Part 2 — The Five Decisions That Changed the Data

These are not stylistic preferences. Each one of them changed what ends up in the database, and four of the five were fixing a bug I did not know I had.

1. ROBOTSTXT_OBEY = True, and an honest User-Agent

# settings.py
ROBOTSTXT_OBEY = True
USER_AGENT = 'RecipeBot (+https://github.com/recipebot)'

The old crawler pretended to be Chrome and never read robots.txt. The target site's file disallows /admin/, /search/, /ingredients/ and query-string recipe URLs, and blocks AI crawlers such as GPTBot and ClaudeBot outright:

User-agent: *
Disallow: /ingredients/
Disallow: /admin/
Disallow: /search/
Disallow: /recipes/*?

User-agent: GPTBot
Disallow: /

User-agent: ClaudeBot
Disallow: /

I was compliant, but only by luck: I happened to point at allowed paths. That is not compliance, it is a coincidence that holds until the next spider. With ROBOTSTXT_OBEY = True every URL is checked against the published rules before the request goes out, and a spider aimed at a disallowed path refuses and logs why. The honest User-Agent is the other half: if my bot is a problem, the site operator can find me and say so, instead of quietly blocking a fake Chrome.

2. No arbitrary page cap

The old crawler carried MAX_PAGES = 15. Any category with more than fifteen pages silently lost the tail. There was no warning, because from the crawler's point of view finishing at page fifteen is exactly what it was told to do.

def parse_category(self, response, category):
    # Extract recipe links, then follow next page
    for link in response.css('article.recipe-card a[href*="recipes"]::attr(href)').getall():
        yield response.follow(link, callback=self.parse_recipe, cb_kwargs={'category': category})

    next_page = response.css('a[rel="next"]::attr(href)').get()
    if next_page:
        yield response.follow(next_page, callback=self.parse_category, cb_kwargs={'category': category})

The site decides when the crawl is done, by stopping to offer a rel="next" link. I now get around 224 recipes per category; before, I got whatever fifteen pages happened to hold.

3. xpath('string()') instead of ::text

Scar

Scrapy's ::text returns only the direct text children of a node. BeautifulSoup's get_text() returns everything underneath. On a page where an ingredient is marked up as <a><strong>Pasta</strong> 00</a>, the new spider extracted "00" and looked like it had worked. Nothing threw. The field was populated. It was just wrong, on exactly the ingredients whose names the site chose to emphasise.

# WRONG: misses text inside <strong>, <em>, etc.
name = dd.css('a::text').get()               # "00"

# CORRECT: gets all text including nested elements
name = dd.css('a').xpath('string()').get('')  # "Pasta 00"

Then normalise the whitespace with ' '.join(text.split()) to match the old clean_text(). The comparison tests are what caught this: the old crawler produced "Farina 00 300 g", the new one "Farina 00 300\n\t\t\t\t\t\t\t\t\t\tg". Two different failures, one selector.

4. Image URLs normalised to the main domain, not the response domain

The ingredient encyclopedia lives on a subdomain but serves its images from the main site. response.urljoin() resolves a relative URL against the domain of the current response, which is the correct general behaviour and the wrong answer here — og:image paths came out pointing at the encyclopedia subdomain, and the downloads failed. The old crawler had a hardcoded rule for this that looked like a hack:

# Old crawler: force all URLs to the main domain
if src.startswith('//'):
    src = 'https:' + src
elif src.startswith('/'):
    src = 'https://www.example.com' + src

It was not a hack, it was knowledge about the site. It survives as a _normalize_url() static method on the spider. Worth remembering when a rewrite tempts you to drop the ugly-looking lines: some of them are the only place a fact about the world is written down.

5. Rule ordering in a substring classifier

classify_ingredient() matches keywords as substrings, which makes the order of the rules part of the logic rather than a matter of taste:

  • "mela" (apple, Frutta) is a substring of "Melanzane" (aubergine, Verdure)
  • "fagiol" (green beans, Verdure) is a prefix of "Fagioli" (beans, Legumi)
  • "pisell" (peas, Verdure) is a prefix of "Piselli" (peas, Legumi)
CATEGORY_RULES = [
    ('Carni',      ['agnell', 'manzo', ...]),
    ('Pesce',      ['salmone', 'tonno', ..., 'rana pescatrice']),
    ('Latticini',  ['mozzarell', 'parmigian', ...]),
    ('Cereali e Pasta', ['pasta', 'spaghetti', ...]),
    ('Erbe e Aromi', ['basilico', 'rosmarino', ...]),
    ('Spezie',     ['pepe', 'cannella', ...]),
    ('Legumi',     ['fagioli', 'lenticchi', ...]),  # BEFORE Verdure
    ('Verdure',    ['carota', 'melanzan', ...]),    # BEFORE Frutta
    ('Frutta',     ['mela', 'pera', ...]),
    ('Condimenti', ['olio', 'aceto', ...]),
    ('Bevande',    ['vino', 'birra', ...]),
    ('Dolci',      ['cioccolato', 'cacao', ...]),
]
Scar

I found "rana pescatrice" — monkfish — sitting in Frutta in production data. Aubergines were there too, because "mela" matched them before the Verdure rule got a turn, and beans and peas had landed in Verdure for the same reason. None of these bugs were introduced by the rewrite; every one of them had been in the old crawler since the beginning, writing wrong rows for months. The rewrite did not create them. It just moved the classifier somewhere I could put a test around it.

The fix is ordering by specificity — Legumi above Verdure, Verdure above Frutta — plus a test that pins the cases I know are adversarial:

class ClassifyIngredientTestCase(TestCase):
    def test_fish_classification(self):
        self.assertEqual(classify_ingredient('Rana pescatrice'), 'Pesce')  # was Frutta
        self.assertEqual(classify_ingredient('Coda di rospo'), 'Pesce')

    def test_vegetable_classification(self):
        self.assertEqual(classify_ingredient('Melanzane'), 'Verdure')      # was Frutta
        self.assertEqual(classify_ingredient('Pomodori'), 'Verdure')

    def test_legumes_classification(self):
        self.assertEqual(classify_ingredient('Fagioli'), 'Legumi')         # was Verdure
        self.assertEqual(classify_ingredient('Piselli'), 'Legumi')         # was Verdure

    def test_unknown_classification(self):
        self.assertEqual(classify_ingredient('Acqua'), 'Altro')

Part 3 — Extraction and Persistence Stop Sharing a Function

The single biggest structural change is not a feature, it is a boundary. In the old scripts, one function owned a page from HTTP request to database commit. Scrapy splits that into three places that cannot see each other's problems.

# Spider: extraction only
yield RecipeItem(
    title=title, url=response.url, ingredienti=ingredienti,
    steps=steps, category=category, ...
)

# Pipeline: persistence only
class RecipePipeline:
    def process_item(self, item, spider):
        self.Recipe.objects.update_or_create(url=item['url'], defaults={...})
        return item

update_or_create keyed on the URL also retires a whole mechanism: the old crawler pre-loaded every known URL from the database into a set to avoid duplicates. Deduplication is now a property of the write, not a data structure the crawler has to carry.

The layout that came out of it:

scrapy_spider/
  settings.py          # ROBOTSTXT_OBEY, AUTOTHROTTLE, honest User-Agent, DJANGO_ALLOW_ASYNC_UNSAFE
  items.py             # RecipeItem, IngredientInfoItem — data contracts
  pipelines.py         # RecipePipeline, DjangoIngredientPipeline, classify_ingredient()
  spiders/
    recipes.py         # RecipeSpider — extraction only, no DB calls
    ingredients.py     # IngredientSpider — extraction only, section-based parsing
run_crawler.py         # Entry point
recipes/tests.py       # 42 unit tests (classification, parsing, helpers, contracts)
python3 run_crawler.py recipes       # Crawl all recipe categories
python3 run_crawler.py ingredients   # Crawl ingredient encyclopedia
python3 run_crawler.py all           # Crawl everything
python3 manage.py test recipes.tests # Run the unit tests

One footnote for anyone driving Django's ORM from a Scrapy pipeline: Scrapy's reactor is async, Django's ORM defends itself against being called from an async context, and the result is a SynchronousOnlyOperation that appears the moment you scale up. DJANGO_ALLOW_ASYNC_UNSAFE = 'true' is the escape hatch, and it is only safe because the pipeline is the single writer.

Part 4 — Proving the Rewrite, and What Is Still Missing

A rewrite of a data-producing system has one obligation: show that the new thing produces the same data as the old thing, field by field, before you delete the old thing. So I ran both crawlers against the same pages and compared everything.

AuditCasesWhat it proves
Recipe comparison20 / 20Every field of a recipe matches the old crawler's output
Ingredient comparison10 / 10Same, for the encyclopedia spider
DB consistency10 / 10What the spider yields is what the pipeline stored
Category classification44 / 44Known ingredient → category mappings, including the fixed ones

That is the 84-case audit, and it was a one-time manual exercise — its job was to let me delete 883 lines of old crawler without wondering. What lives on in CI is a suite of 42 unit tests in three layers: pure helper functions (classify_ingredient(), truncate_at_sentence(), match_section()), parser tests that feed mock HTML to a spider method and assert on the yielded item, and contract tests that assert every required field is populated.

The middle layer is the one that pays for itself, because it needs no network:

class RecipeSpiderParseTestCase(TestCase):
    def test_parse_recipe_basic(self):
        spider = RecipeSpider()
        json_ld = json.dumps({"@type": "Recipe", "estimatedCost": "Basso",
                              "prepTime": "PT20M", "cookTime": "PT15M",
                              "recipeYield": 4, "image": "https://example.com/img.jpg"})
        html = f'<html><body><h1>Pasta al Pomodoro</h1>...<script type="application/ld+json">{json_ld}</script>...</body></html>'
        response = HtmlResponse(url='https://...', body=html.encode('utf-8'))
        results = list(spider.parse_recipe(response, category='Primi'))
        self.assertEqual(len(results), 1)
        self.assertEqual(results[0]['title'], 'Pasta al Pomodoro')
        self.assertEqual(results[0]['difficulty'], 'Facile')
        self.assertEqual(results[0]['servings'], 4)

The gap I have not closed

Everything above protects me from my own changes. None of it protects me from the site's. If the target renames dd.recipe-ingredient to dd.ingredient-list tomorrow, my selectors do not raise — they return nothing, the item is still yielded, the pipeline still writes it, and the database fills up with recipes that have no ingredients. That failure looks identical to a successful crawl in every log line I currently produce.

The dangerous failure in a scraper is never the exception. It is the empty list that passes for data.

Three things would close it, in the order I intend to build them. Frozen fixtures: commit a handful of representative pages to tests/fixtures/ and run the parser tests against those, so CI stops depending on a live site and starts detecting my regressions deterministically. A schema-drift check against the real site, run weekly rather than per commit, whose assertions are about plausibility instead of exact values — a recipe with fewer than three ingredients or fewer than two steps means a selector broke, not that the recipe is unusual:

class RecipeSchemaTest(TestCase):
    """Hits the real site — weekly job, not every commit."""
    def test_selectors_still_valid(self):
        item = list(RecipeSpider().parse_recipe(
            fetch_live('https://example.com/risotto.html'), category='Primi'))[0]
        self.assertGreaterEqual(len(item['ingredienti']), 3,
            f"Got {len(item['ingredienti'])} ingredients. Selectors may have broken.")
        self.assertGreaterEqual(len(item['steps']), 2,
            f"Got {len(item['steps'])} steps. Selectors may have broken.")

And a classification snapshot that grows by one line every time I touch a keyword: a frozen map of known ingredient-to-category answers, so nothing can quietly send monkfish back to Frutta. The rule I am holding myself to is that adding a keyword means adding its case.

Key Takeaways

  1. The framework question is about the middle layer, not the HTTP call. httpx and parsel match Scrapy at the top and bottom of the stack. Everything between — scheduler, dupefilter, retries, throttling, pipelines, resume — is what you are volunteering to write and maintain.
  2. Read robots.txt, and say who you are. Compliance by coincidence stops holding the moment you add a spider. An honest User-Agent means the site can complain to you instead of blocking you.
  3. Hardcoded limits lose data silently. MAX_PAGES = 15 never errored; it just quietly discarded the tail of every long category. Crawl until the site stops offering a next page.
  4. ::text drops text inside nested tags. Use xpath('string()') anywhere the source markup has <strong> or <em> inside the node you are reading, then normalise whitespace yourself.
  5. In a substring classifier, rule order is logic. "mela" matches "Melanzane". Order by specificity and write the adversarial cases down as tests, because the next person to add a keyword will not remember why.
  6. Ugly lines in old code often hold facts about the world. The hardcoded image domain looked like a hack and was actually the only record that one subdomain serves another's images.
  7. Separate extraction from persistence and both become testable. Spiders yield items, pipelines write them; the parser can then be tested with a saved page and no database at all.
  8. Audit a rewrite field by field before deleting the old one. Comparing both crawlers on the same pages is what surfaced the nested-text bug — and the old crawler's own bugs, which had been writing wrong rows for months.
  9. Assert plausibility, not just success. A scraper's worst failure mode returns a well-formed item with an empty list inside it. Only a check that knows a recipe has at least three ingredients can see that.
