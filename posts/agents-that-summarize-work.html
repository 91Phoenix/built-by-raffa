Out of the Dumb Zone: Engineering Agents That Summarize Real Work

September 2026 · 25 min read

The task sounds simple enough to be a weekend project: given everything an engineer did in a quarter — the changes they authored, the reviews they left, the issues they worked, the support threads they answered — write a few paragraphs that describe their work the way a colleague would.

It is not a weekend project. It is the hardest engineering problem I have worked on that contains almost no algorithms. The data platform underneath it I have written about separately; this post is only about the agents: five versions of the same feature, each one fixing what the previous one got wrong about context, cost, consistency or trust.

Anonymized as usual — no employer, no service names. What transfers is the sequence, because I think most teams building agents on real data walk it in the same order, and it is cheaper to read about it than to discover it.

Version 1 — Chunk It, and Summarize the Summaries

The first version is the one everybody writes. Fetch everything the person did. It does not fit in the context window. So chunk it, summarize each chunk, then summarize the summaries.

This works, in the sense that it produces text. Two things are wrong with it, and only one is obvious.

The obvious one is cost and latency: you are paying for every token of raw material, twice, and a quarter of activity for a busy engineer is a lot of tokens.

The non-obvious one is that arbitrary chunks destroy the structure the reader cares about. If you chunk by date, one migration that took three weeks gets split across four chunks, each of which produces a bland paragraph about "various changes", and the final pass summarizes four bland paragraphs into one blander one. The output is fluent, accurate in the narrow sense, and says nothing.

The fix that made the difference was not a better model. It was grouping by theme before summarizing: cluster the contributions into coherent bodies of work first, summarize each theme from its own items, then compose the themes. Same number of model calls, completely different output, because the unit the summarizer sees is now the unit a human recognizes. "Led the migration of the notification path off the legacy queue" instead of "made changes in March".

Hierarchical summarization is only as good as the hierarchy. Chunking is a memory constraint; grouping is a modelling decision. Do not let the first one silently become the second.

Four data types, four agents, four prompts

The other structural decision, and the one I would make earliest if I started again: one agent per kind of contribution, each with its own prompt, its own tools and its own idea of what evidence means — authored changes, code reviews, issues, and chat threads.

The temptation is the opposite. One agent, one prompt, "summarize this person's work", and let the model figure out the differences. It does not, and the reason is that these four sources disagree about almost everything that matters to a summarizer:

SourceUnit of evidenceWhat the prompt has to get rightFailure if you use a generic prompt
Authored changesOne change, plus its description and diff digestWhat changed and why; escalate to the diff when the description is thinRestates commit titles
Code reviewsOne review, in someone else's changeThe contribution is the influence — what the review caught, what changed because of it — not the subject matter of the changeDescribes other people's work as if it were theirs
IssuesA thread with a life cycle and a resolutionTheir role in it: reported, triaged, diagnosed, fixed, closedSummarizes the bug, not the person
Chat threadsA slice of a multi-party conversationWhich messages are theirs, what followed them, whether the thread converged afterRewards whoever typed the most

Reviews are the clearest case. Forty reviews and three authored changes are both real quarters, and a prompt written for authorship will describe the reviewer as though they built the forty things they commented on. The review agent needs the opposite instinct: the change is context, the comment is the contribution, and the interesting signal is what happened to the change afterwards.

Separating them buys three things beyond output quality:

  • Each prompt gets tuned against its own evidence. When the evaluation set is sliced by source, a regression in review summaries is visible instead of being averaged away by good authorship summaries.
  • Each agent gets its own tools and its own model tier. The chat agent needs message-level structure and careful reasoning; the authorship agent needs the diff-escalation tool. Neither has to carry the other's instructions in context.
  • They run and fail independently — which is also what makes the asynchronous runtime below able to return partial results.

The composition step is then the only place that has to hold all four at once, and its job is narrow: weigh the sources against each other and write the overall narrative. That is a much easier prompt to write than one that has to be four prompts wearing a trenchcoat.

Version 2 — Stop Stuffing the Context, Give the Agent Tools

The second realization: pushing all the data at the model is the wrong direction of control. Most of what you push is never needed for the conclusion, and you pay for it in money, latency and — the expensive one — attention.

So we inverted it. The agent got tools with pagination: list contributions for a period, fetch the detail of one, fetch the linked discussion. The agent decides what to open.

Tool design rules we converged on, all of them learned by having them wrong first:

  • List endpoints return identifiers and a handful of fields, never bodies. A list call that returns full diffs is context-stuffing with extra steps.
  • Pagination is a context control, not an API convenience. Cap the page size server-side. A model given limit will eventually ask for a very large one, and the tool must be the thing that says no.
  • Ordering must be deterministic and meaningful — by relevance where you can compute it, by time otherwise. Non-deterministic ordering makes runs irreproducible, which makes evaluation meaningless.
  • Filters beat pages. Every filter you add (by repository, by theme, by date range) is a page the agent never has to fetch.
  • The tool description is part of the prompt. It is in the context on every turn, and it is where the model learns when not to call the tool. We later optimized these descriptions automatically — see below — and the gains were comparable to optimizing the prompts themselves.

Escalate to the expensive evidence only when the cheap evidence is thin

The tool that paid for itself fastest was the one that reads the diff.

Most changes come with a description, and when the description is good, it is by far the cheapest and best evidence available: a human already did the summarization, in the right vocabulary, at the right altitude. The agent should use it and move on.

But descriptions vary wildly. Plenty of changes ship with a title, a ticket reference and nothing else — and some of those are the most substantial work in the quarter, because the engineer who rewrote the scheduler's locking was concentrating on the scheduler's locking, not on writing prose about it. Summarizing from the description alone systematically under-describes exactly the work you most want to describe.

So the agent escalates, conditionally: when the available description is too thin to support a claim, it calls a tool that fetches the change itself — the file list, the shape of the diff, the review discussion — and reasons from that instead.

Three properties make this work rather than just move the cost around:

  • It is the exception, not the default. The majority of changes never trigger it. Fetching every diff for every contribution would be the most expensive possible version of this system; fetching the ones where the cheap evidence is insufficient costs a fraction and lifts the quality where quality was actually missing.
  • The tool returns a digest, not raw bytes. Paths and the counts per area, the interesting hunks, the discussion — not four thousand lines of generated code, lockfile churn and formatting. The pre-processing rule from the next section applies with full force here: a program decides what part of a diff is worth a token before the model ever sees it.
  • The escalation criterion belongs in the prompt and is worth tuning. "Fetch the diff when the description does not let you state what changed and why" is a judgement call, and the boundary moves the cost curve a long way in both directions. It was one of the instructions the optimization loop later improved on its own.

The generalization I would take to any agent over mixed-quality data: rank your evidence sources by cost and let the agent walk down that list only as far as it needs to. Cheap summary first, expensive ground truth on demand. Uniform depth is either wasteful everywhere or shallow everywhere, and you rarely get to pick which.

Interlude — A Conversation Is Not a Document

The source that broke the most assumptions was not code. It was conversations: support threads and issue discussions.

The naive treatment is to concatenate a thread and summarize it, which answers the question "what was this thread about". That is genuinely useful — and it is the wrong question, because the thing we needed was what was this person's contribution to it. Those are different summaries of the same text, and the first one is nearly useless for the second.

Consider a thirty-message thread about a failing deployment. Depending on which messages are theirs, a participant might have:

  • asked the original question — they had the problem, they did not solve it;
  • diagnosed the cause in message eleven, after which the thread converged;
  • provided the fix, or provided the context that let someone else find the fix;
  • routed it — pulled in the team that owned the system, which is real and frequently invisible work;
  • been mentioned, and never replied at all.

Every one of those produces the same thread-level summary and a completely different statement about the person. Getting this wrong is not a cosmetic error: it credits people for being present in busy channels and misses the person whose one message ended a three-hour incident.

What the analysis has to preserve, therefore, is the message-level structure: who wrote what, in what order, in reply to what, and what happened after. Concretely:

  1. Keep authorship and position. The messages are attributed and ordered before they reach the model, and the person being summarized is marked in the transcript. Anonymized or flattened text makes the question unanswerable.
  2. Distinguish opening from resolving. The first message and the message the thread converges on play opposite roles, and only the ordering tells you which is which.
  3. Treat the reaction as evidence. What follows a message — the thread stopping, someone saying that fixed it, the issue closing shortly after — is the strongest available signal of impact, and it is structural, so a program can surface it.
  4. Do not reward volume. Ten clarifying replies are not more contribution than one correct diagnosis. Left alone, a summarizer will describe the person with the most text, because that is what it saw most of. This has to be stated explicitly in the prompt and checked explicitly in the evaluation.
  5. Resolve identity before reasoning. The same human has a chat handle, a source-control account and a directory entry. If those are not joined upstream, the agent sees three people and describes none of them correctly.
The principle

For code, the artifact is the contribution. For a conversation, the artifact is the thread and the contribution is a slice of it — which means the summarization target and the evidence unit are different objects. Any pipeline that treats a discussion as one blob of text has already thrown away the only thing that made it worth summarizing per person.

Version 3 — Do in Code What Code Does Better

The third version was mostly deletion of model calls.

A surprising share of what the early agents did was work a program does faster, cheaper and correctly every time: deduplicating records, dropping automated accounts, resolving a person to the team they were on at the time, joining a change to the deployment that shipped it, counting things, ranking by a relevance score, truncating a 4,000-line diff to the parts that carry signal.

None of that is judgement. All of it was being done, badly and expensively, inside a context window.

The rule

Use the model for judgement, and code for everything else. Judgement is: what were the themes, what mattered, how would you describe this to a colleague. Filtering, joining, counting, sorting, deduplicating and truncating are code. Every token of boilerplate you hand the model you pay for twice — once at the invoice, once in the attention budget you had left for the actual reasoning.

The practical effect of the pre-processing layer was that the agent's context went from "everything this person touched" to "these twelve candidate themes, with their strongest evidence attached, ranked". The quality went up because the model had room to think, and the cost went down by an order of magnitude. Those two usually trade against each other; here they did not, which is the signature of having been wasteful rather than ambitious.

Context management: files, fresh sessions, compaction

The related discipline is what to do when the work genuinely does not fit — a very active engineer, a whole team, a year rather than a quarter.

Three techniques, in the order we reach for them:

  1. Write intermediate results to files and read them back deliberately. The per-theme summaries do not need to stay in the conversation; they need to exist when the composition step runs. Storage is memory that does not degrade.
  2. Start a fresh session per unit of work. One session per theme, with only that theme's evidence, beats one session that has seen everything. A fresh context is not a limitation to work around; it is a way to guarantee the model is looking at the right material.
  3. Compact when continuity is genuinely needed. Summarize the conversation so far into a short brief and continue from that, rather than carrying the raw history.

The thing all three protect against is what I have come to call the dumb zone: the region where the context is technically within the model's window but well past the point where it reliably uses what is in it. Recall of material in the middle degrades, instructions given early get overridden by noise arriving later, and the failure is silent — you get a confident, fluent, subtly worse answer. There is no error, no truncation warning, nothing in a log. Just a decline in quality that only an evaluation harness will catch.

So: budget context like RAM. Know roughly what the working set is for each step, keep it well under the window rather than near it, and treat "it still fits" as a very weak argument.

Version 4 — The Judge, and What It Is Allowed to Reward

By this point the system produced good output. Sometimes. The remaining problem was consistency: the same person's quarter, generated twice, could produce one excellent summary and one that was vague, or that leaned on a minor piece of work because it happened to have more text attached.

You cannot improve what you cannot score, and "is this a good description of someone's quarter" has no reference answer to diff against. So we built an LLM-as-judge harness: a fixed evaluation set, a rubric, and a judge model that scores each generated summary.

The rubric mattered more than the judge. The dimension that did the most work was evidence: does every substantive claim carry a link to the thing it came from — a pull request, a review, a support thread — and does the linked artifact actually support the claim?

Why that one, above fluency or coverage:

  • It is the closest thing to an objective signal available. Link present, link resolves, link's content matches the sentence — those are checkable, and two of the three are checkable in code without a model at all.
  • It is what makes the output usable. A claim about a person's work that you cannot trace is not a summary, it is an opinion with good grammar.
  • It directly attacks the dangerous failure mode. These systems do not usually fail by being obviously wrong; they fail by being plausible. Requiring a citation per claim makes plausibility expensive.

Practical notes on running a judge, all of which cost us something to learn:

  1. Judge with a different model than the one generating where possible. Models have a measurable preference for their own output, and a judge that likes its own style rewards style.
  2. Check mechanically what you can check mechanically. Link presence, link resolution, whether cited artifacts belong to the person being summarized — all of that is a script. Save the model for "does this text match this evidence".
  3. Calibrate against humans once, properly. Have people score a sample, compare to the judge, and adjust the rubric until they correlate. A judge nobody has calibrated is a random number generator with a PhD voice.
  4. Version the eval set and freeze it. A score is only comparable across runs if the questions did not change.
  5. Gate on regression, not on absolute score. "Did this change make it worse" is answerable and useful; "is 7.4 good" is neither.

Version 5 — Evolving the Prompts (and the Tool Descriptions)

With a score in place, prompt engineering stops being taste and becomes optimization. And once it is optimization, doing it by hand is a strange choice.

We based this part of the work on GEPA — Genetic-Pareto reflective prompt evolution (arXiv:2507.19457). The idea: run the system, capture the full trajectories including tool calls and their outputs, have a model reflect in natural language on what went wrong, propose edits to the instructions, test them against the evaluation set, and keep a Pareto frontier of candidates rather than a single best one, so complementary improvements can be recombined instead of competing.

The paper's headline result is the reason we took it seriously rather than treating prompt search as a toy: across their tasks, GEPA outperformed GRPO — a reinforcement learning approach — by around 10% on average and up to 20%, while using up to 35× fewer rollouts, and beat the leading prior prompt optimizer by over 10%. The interpretation I find convincing is the one they argue: a natural-language reflection on a failed trajectory carries far more information than a scalar reward does. A reward says "that was worth 0.3". A reflection says "it summarized the review work without citing a single review, because the instruction only demanded citations for authored changes".

Crucially, this runs per agent. The authorship agent, the review agent, the issue agent and the chat agent each have their own prompt, their own tool descriptions and their own slice of the evaluation set, so each one is optimized against the failures that are actually its own. A single global score would have hidden exactly the problem we most wanted to fix — review summaries drifting into describing other people's changes — underneath a healthy average.

Two things surprised me in practice.

First, optimizing tool descriptions mattered as much as optimizing prompts. The description is the model's only documentation for a capability; a sentence clarifying when not to call a tool, or what the pagination actually returns, removed whole classes of wasteful trajectory. Most teams hand-write these once and never touch them again. They are prompt surface, and they should be in the optimization loop.

Second, the output of all this is text. No weights, no training infrastructure, no GPU budget, no model to host. The optimized artifact is a prompt and a set of tool descriptions that a human can read, review in a pull request, and revert. For a platform team that has to explain the system to its users, that reviewability is worth a great deal on its own — independently of the accuracy numbers.

The Economics: Evals Are What Let You Not Use the Newest Model

Running an agent per person per period across a whole engineering organisation is not a demo budget. Cost is a design constraint, and it shows up as a specific discipline: the evaluation harness must run against several models, not just the newest one.

The reasoning:

  • Different steps need different capability. Theme clustering, per-theme summarization, final composition and judging are four jobs with four difficulty levels. Using one frontier model for all of them is paying premium rates for the easy three.
  • A prompt tuned exclusively against the newest model is quietly coupled to it. When it is deprecated, repriced or rate-limited, you find out how coupled.
  • You cannot safely downgrade a step without evidence, and the eval harness is the evidence. With it, "can this step run on the cheaper model?" is a ten-minute experiment with a number at the end. Without it, it is an argument.

So the rule we adopted: every agent step declares a model, the evals run across the tiers, and a step uses the cheapest model that passes its bar. The frontier model is for the steps that genuinely need it — in our case, composition and judging — and not for extracting fields from a payload.

The same discipline covers the upgrade direction, which people forget. When a new model appears, the eval set tells you within an hour whether it is better for your task, rather than better on someone else's benchmark. Several times the honest answer was "not enough to justify the change".

The Runtime: Asynchronous by Construction

None of this can run inside a request. A summary takes minutes: many model calls, tool calls, retries. Any design where a user's HTTP request is waiting for it is broken before it ships — and worse, a retry re-runs the whole expensive thing.

Details worth copying:

  • The request is a row with a state, not an in-flight connection. Pending, running, partial, ready, failed. The UI renders the state honestly — "generating the review summary" beats a spinner that might already be dead.
  • Each source agent is its own worker and posts its own result. Partial results are useful, and a failure in one source does not discard three that succeeded.
  • Requests are deduplicated and results are cached with a policy. Two people asking for the same summary in the same hour is one generation. Regeneration is explicit, because a user who asks again usually wants a new answer, not the cached one.
  • Permissions are checked at generation and again at read. Reporting lines change; a summary generated when someone was your report must not remain readable when they are not.
  • Trajectories are stored. Every improvement in the previous sections depends on being able to look at what the agent actually did, on a real request, weeks later.

The Same Machinery, Pointed at Money — and Then Not Shipped

Once the pipeline existed, it was obviously reusable: pre-process programmatically, cluster, summarize with evidence, judge, tune. So we pointed it at a finance-adjacent question — estimating how engineering effort distributed across product features, the kind of number that feeds capitalization and planning.

Technically it worked. It combined availability data with contribution data, produced per-feature effort estimates with the evidence attached, rolled up per team, and was reviewable and editable by the people it described.

We decided not to take it further.

The decision

The output was defensible only with human review in the loop, and the pull towards using it without that review was strong — because a number in a spreadsheet does not carry its caveats with it. We had already learned, with the metrics product, what happens when something powerful ships without an explicit statement of what it is not for: managers used our figures in performance reviews, nobody asked us, and nothing in the product stopped them. An effort-allocation estimate lands in a context where the incentives to shape the input are immediate and obvious. So the right engineering decision was to stop, and to say why.

I count that as one of the better calls I have been part of, and it is worth saying plainly because the industry incentive runs the other way: the interesting question about an agent is not "can it produce this output" — increasingly the answer is yes — but "what happens to the people described by the output when someone treats it as authoritative". If the honest answer is "something bad, and the guard rails are advisory", the feature is not ready, however good the evals look.

Key Takeaways

  1. Summary-of-summaries is version one, not the design. Chunking is a memory constraint; grouping by theme is the modelling decision that makes the output mean something.
  2. One agent per data type, with its own prompt, tools and eval slice. Authored changes, reviews, issues and chat threads disagree about what counts as evidence and what counts as impact — a review prompt that borrows the authorship prompt credits people with other people's work.
  3. Optimize and score per agent, not globally. One blended score hides the source whose summaries are drifting.
  4. Invert the data flow: give tools with pagination instead of stuffing context. Cap page sizes server-side, order deterministically, and prefer filters over pages.
  5. Tool descriptions are prompt surface. They are in context every turn and they teach the model when not to call — put them in the optimization loop.
  6. Rank evidence by cost and escalate only when the cheap evidence is thin. A good change description is the best and cheapest summary you will get; fetch the diff when it is missing, return a digest rather than raw bytes, and tune the escalation criterion.
  7. A conversation is not a document. Summarizing a thread answers a different question from summarizing a person's contribution to it — keep authorship, ordering and what happened next, and never let volume stand in for impact.
  8. Use the model for judgement and code for everything else. Deduplicating, joining, counting, ranking and truncating are programs.
  9. Budget context like RAM. Files for intermediate state, a fresh session per unit of work, compaction when continuity is genuinely needed.
  10. The dumb zone is silent. Fitting in the window is not the same as being used well; only an eval harness detects the decline.
  11. Score before you tune. A frozen eval set and a judge turn taste into optimization.
  12. Make citations the primary rubric dimension. A claim about someone's work that cannot be traced is an opinion with good grammar — and link checks are largely mechanical.
  13. Judge with a different model, calibrate against humans once, gate on regression. An uncalibrated judge is a confident random number.
  14. Reflective prompt evolution is a serious optimizer. GEPA reports beating GRPO by ~10% on average with up to 35× fewer rollouts — natural-language reflection carries more signal than a scalar reward.
  15. The optimized artifact is reviewable text. No weights, no training infrastructure, and you can revert it in a pull request.
  16. Evals are what let you not use the newest model. Per-step model choice, cheapest that passes the bar, and an hour to evaluate whether a new release is actually better for your task.
  17. Agents are asynchronous jobs. A row with a state, one worker per source posting partial results, dedup, explicit regeneration, permissions at read time, trajectories stored.
  18. Ask what happens when someone treats the output as authoritative. If the guard rails are advisory and the answer is "something bad", not shipping is the engineering decision.
