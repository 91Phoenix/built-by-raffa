Where Did the Build Time Go? Tracing a Distributed CI System

September 2026 · 12 min read

"The build took 22 minutes." That sentence arrived in our support channel several times a day, and for a long time we could not answer the only question that follows it: 22 minutes of what?

The build itself — the compiler, the tests — was often four of those minutes. The rest was distributed somewhere across a webhook that waited in a queue, a scheduler that took its time picking the event up, a module discovery phase parsing build configs, a pod that had not been scheduled yet because the cluster was full, an upstream module the build was waiting on, and a finish event that took a while to be processed after the container had already exited. Six candidates, no evidence, and a support conversation that always ended with "we'll look into it".

So we built tracing for it. Not application tracing of HTTP requests — that existed — but tracing of the build as the unit of work, spanning several services, a queue, a Kubernetes cluster, and a lifecycle measured in minutes rather than milliseconds. This post is the design, what it revealed, and the second half of the story: the cluster controller whose API traffic the tracing exposed.

Anonymized as usual: no employer, no service names. The shape is what transfers.

Why Off-the-Shelf Tracing Didn't Fit As-Is

Standard distributed tracing assumes a request: it starts, it fans out, it ends, it lives for milliseconds, and you sample it because you have millions and care about the shape of the distribution.

A build violates all of that:

  • It lives for minutes to hours, and the interesting part is often the gap between two spans, not a span.
  • It crosses a process boundary through a queue and a database row, not a header on an HTTP call.
  • Nobody wants a sampled answer to "why was my build slow". Sampling is the wrong default when each trace corresponds to a human waiting.
  • The questions are as much analytical as diagnostic: "what is the median queue wait per cluster this month" is a SQL question, not a trace-viewer question.

So we kept the tracing API — spans, tags, a method interceptor that traces annotated methods and pulls identifiers out of the arguments — and replaced everything underneath it.

Spans over Kafka, not to a collector

The tracer's span reporter was replaced with one that converts spans to a protobuf message and publishes them to a topic. That one change bought three things: producers never block on a tracing backend being up, retention becomes a topic configuration rather than a vendor setting, and — the real reason — the topic already lands in object storage, which makes every trace queryable with SQL.

Two schema decisions I would make again. First, the span's key-value tags are all strings, with a separate type field, rather than a union of typed values. Traces are written by many services and read by ad-hoc queries; a uniform column type makes the SQL trivial and the schema boring. Second, the tag keys are an enum, not free strings. The moment tag keys are free-form, you have twelve spellings of "module" and no aggregation.

Significant events: the tags that made analysis possible

Raw spans tell you when methods ran. They do not tell you what the build was doing, which is what a human asks. So the model has a small enum of significant events — the state transitions worth measuring — and the converters tag spans with them.

The single most valuable one, and it took a round of confused analysis to discover it was missing: distinguishing waiting for a previous build of the same module from queued because the cluster was busy. Both look like "not running yet". One is a serialization constraint the system imposes deliberately; the other is a capacity problem. We had been averaging them together and drawing the wrong conclusion about what to fix.

A second one, subtler: recording the end of the last executor step as its own event, separate from the module build's end. The gap between them is the time between the container finishing and the scheduler processing the finish event — time that is invisible to the executor, invisible to the user, and entirely ours. It turned out to be worth measuring.

From Traces to Insights: the Document That Made It Usable

Traces are the raw material, not the product. Nobody wants to write SQL to learn why their branch is slow. So a job read the previous day's traces for every branch that built, assembled a per-build breakdown in memory, and wrote one small insight document per branch per day into object storage under a date-partitioned key.

That document is what the API serves and what the charts render: a timeline of the build and a per-module breakdown, rendered server-side as an HTML page with interactive charts. Unglamorous and effective — an engineer could open their branch and see the shape of their build without learning a query language.

Three refinements, each caused by production reality rather than design:

  • Empty results are a normal case. The first version of the job assumed every branch it asked about had traces. Branches go quiet; the query returns nothing; the job fell over. Resilience to "no data" is a feature, not an error path.
  • Sanitize before you visualize. A handful of traces per day carried malformed build numbers. The job initially failed the whole day's insights on them. Skipping the bad trace and producing insights for the rest is almost always the correct trade in an analytics pipeline.
  • Make the target date a parameter. Obvious in hindsight; essential in practice. Every backfill, every "re-run yesterday because we fixed the converter" depends on it.

Then the architecture shifted: instead of a nightly job being the only producer, insight documents started being written as builds finished. Same document, same location, same readers — but available immediately. The nightly job stayed for reprocessing. That is the nice property of having made the insight document a first-class artifact in storage: you can change who writes it without changing anything that reads it.

What the Traces Actually Showed: Delay Metrics and SLAs

Once the trace data existed, the useful output was not a flame graph. It was a small set of delay metrics, each measuring one hand-off:

DelayFrom → toWho owns it
Push delayCommit pushed → event processedWebhook path and queue depth
Discovery delayEvent processed → module discovery startsScheduler capacity
Discovery-to-launchDiscovery done → repo build launchedScheduler logic
Executor waitModule build runnable → container runningCluster capacity and pod provisioning
Upstream waitRunnable-but-blocked → unblockedThe dependency graph, not the infrastructure

This decomposition is the entire payoff of the project. It turned "CI is slow" into six numbers with six different owners, which meant we could define an SLA per stage and argue about capacity with evidence instead of anecdote. It also made prioritization mechanical: fix the stage with the worst p95 against its target, not the stage the loudest person complained about.

We added configurable thresholds so builds exceeding them logged themselves for investigation, which is a much better on-call signal than an aggregate dashboard: a dashboard tells you the p95 moved, a threshold log tells you which build to open.

The rule I'd keep

Instrumentation must never be able to break the thing it instruments. The tracing interceptor wraps everything it does in exception handling: a failure to trace is a dropped trace, never a failed build. That sounds obvious until you notice how many tracing libraries will happily throw out of a method they were only supposed to be observing.

The Other Half: the Controller That Was Talking to Kubernetes Too Much

Build pods were created and destroyed by a controller sitting between the scheduler and the cluster. It decided how many pods of each size each cluster needed, created them, watched them, and cleaned them up. Under load it got slow, and when it got slow, builds queued — which showed up, precisely, as executor-wait delay in the traces above.

The root cause was not clever. It was talking to the Kubernetes API far more than it needed to.

  1. Listing pods once per cycle instead of once per question. Demand calculation fetched the pod list repeatedly within a single execution — roughly twice per container size plus once per executor cluster. Caching the list for the duration of one cycle reduced that to two calls, total.
  2. Deleting a code path nobody needed. A semaphore mechanism in the pod watcher had been made redundant by an earlier change but was still issuing calls — on the order of 50 to 60 requests per second, millions per day, for nothing. This is the most common shape of infrastructure waste I have seen: not a bad algorithm, a leftover.
  3. Watching five times less often. The watch-and-wait loop ran ten times a second. Two was indistinguishable in behaviour, and the delay became configurable so the next person does not have to redeploy to find out.
  4. Counting only pods that consume capacity. Completed pods were being counted against pod demand, so the controller throttled creation because of pods that had already finished and were holding no resources.

The thread pool that blocked itself

The subtlest problem: pod creations and deletions were published on one in-process event bus with one shared thread pool. When the Kubernetes API slowed down at peak — which is exactly when the system is busiest — delete operations saturated the pool, and create operations queued behind them. The cluster had capacity; builds waited anyway.

Two independent pools fixed it, plus asynchronous listeners so a single slow event cannot block the others behind it. This is a general rule worth stating plainly: operations with different latency profiles and different urgency do not belong in the same pool. A deletion is cleanup; a creation is a person waiting. Sharing a pool means the cleanup can starve the person.

And then the refactor that made it ordinary

Eventually the watcher components came out entirely and the deletion logic moved into the controller, with creation and deletion done the same way, in one place, following the standard worker pattern used by every other service we ran. Plus explicit handling for init-container failures, which had previously been a silent way for a pod to be counted as alive forever.

That last change delivered no measurable improvement on the day it shipped, and it was one of the most valuable things we did: it turned a bespoke component that only one person fully understood into an ordinary one with the same shape as everything else on the team.

Then measure the controller itself

Once the structure was right, we instrumented it: pod creation latency and rate, deletion latency and rate, how long fetching pod information takes, and — the one I would add first next time — the delay introduced by the event bus itself, separately for creates and deletes. Without that last metric, a queue inside your own process is invisible: every individual operation looks fast, and the system is still slow.

Two bugs the metrics surfaced. Pod creation exceptions (an admission webhook denial, for instance) were not incrementing the create counter, so the controller's own idea of capacity drifted from reality. And nothing was reporting creation failures to the error tracker, so a class of failure was only visible in logs nobody was reading.

The cost lever, in one line

After all of that, the change with the biggest financial impact was reverting the CPU allocation per executor pod to half of what it had been — about a 50% reduction in the cost of the build fleet — once the throttling data showed the larger allocation was not buying the throughput it was supposed to. The lesson is not "make pods smaller". It is that a resource allocation set during an incident is a hypothesis nobody re-tested, and re-testing it is often the cheapest money you will ever find.

Key Takeaways

  1. Trace the unit of work your users name. For CI that is the build, not the HTTP request. The interesting part is the gaps between spans.
  2. Ship spans through your existing event backbone. Producers stop depending on a tracing backend, retention becomes a topic setting, and the data lands where SQL can reach it.
  3. Enumerate tag keys and keep values uniformly typed. Free-form tags make aggregate analysis impossible later.
  4. Name the state transitions, not just the method calls. A small enum of significant events is what turns spans into answers.
  5. Separate "blocked by a dependency" from "waiting for capacity". They look identical and they have different owners.
  6. Make a small, stable derived document the product's interface. Then you can change who produces it — nightly job, then real-time — without touching readers.
  7. An analytics job must tolerate empty and malformed input. Skip the bad trace, produce the rest, and make the target date a parameter.
  8. Decompose latency into per-stage delays with owners. That is what makes an SLA arguable and prioritization mechanical.
  9. Instrumentation must never break the instrumented. Catch everything inside the interceptor.
  10. Most API-traffic waste is leftovers, not algorithms. Look for the code path a previous change made redundant.
  11. Never share a thread pool between cleanup and user-facing work. Cleanup will starve the user at exactly the worst moment.
  12. Measure your internal queues. If every operation is fast and the system is slow, the wait is in a pool you are not instrumenting.
  13. Re-test resource allocations set under pressure. Halving a fleet's CPU request after checking the throttling data was the cheapest win of the year.
