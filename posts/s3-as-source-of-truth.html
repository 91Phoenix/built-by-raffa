Object Storage as the Source of Truth: An Engineering Data Platform, and the Agents on Top of It

September 2026 · 16 min read

After years on build infrastructure I moved to a team with a different problem: not "make this system fast", but "make this organisation legible". We collected engineering activity data — pull requests and reviews, deployments, incidents, support interrupts, tool usage — and turned it into something teams and leaders could act on, at three granularities: the individual, the team, the org.

The application people saw was charts. Underneath was an ETL platform: scheduled jobs pulling from a dozen sources, raw records landing in object storage, a framework ingesting them into the warehouse, and a modelling layer refining them into the tables the product queried. Later, on top of the same data, an agentic system that produced narratives instead of numbers — which turned out to be both the most interesting engineering and the most delicate product decision I have been part of.

This post is both halves. Anonymized: no employer, no service names, no internal links.

Part 1 — The Pipeline

Why object storage is the source of truth and the warehouse is not

The first architectural decision, and the one everything else depends on: raw records land in object storage first, and the warehouse is a materialization of that, never the other way round.

It is tempting to skip the middle step. The sources have APIs, the warehouse has a loader, why keep a copy of everything in a bucket? Four reasons, all of which we hit:

  • Sources are lossy and rate-limited. Re-fetching two years of history from an API because you added a column is not a backfill, it is a project. Re-reading your own bucket is an afternoon.
  • Schema evolution is continuous. Every model change is a reprocessing job. If the raw event is stored, reprocessing is deterministic and free of the source's opinions.
  • Warehouses are for querying, not for remembering. Table rebuilds, migrations, cost-driven retention changes — all of these are safe when the warehouse is derived, and terrifying when it is primary.
  • Auditability. When someone disputes a number — and with this kind of data, someone always disputes a number — you want to show them the record as the source produced it, not your interpretation of it.

The small-files problem, which you will hit on day one

The first version wrote one object per record: one pull request, one file. It is the obvious implementation and it is wrong in two directions at once. The warehouse loader chokes on enormous numbers of tiny files — per-file overhead dominates and ingestion falls behind. And backfills become pathological: writing a year of history one object at a time takes longer than fetching it did.

The fix is to batch by the natural grain of the source: a day of deployments, a day of pull requests for a repository, a channel's threads for a day. Then generalize the batching mechanism once, so every new source inherits it rather than reinventing it. The key layout matters too — org/repo/yyyy/mm/dd rather than a flat namespace — because every reprocessing job you will ever write is scoped by time, entity, or both, and the prefix is the only index object storage gives you.

Concurrency: a lock table, and a watchdog for the lock table

Multiple writers — a live worker and a backfill job, two backfills for adjacent ranges — can target the same repository's prefix at the same time and interleave into a mess. We serialized writes per repository with a lock row in a relational database.

And then, inevitably, the second half: a watchdog that clears stale locks. A process that dies holding a lock blocks that repository forever, and "forever" in a data pipeline means "until someone notices the numbers stopped moving", which can be a week. Any lock held by a process that can crash needs an owner, a timestamp, and something that reaps it. If you build the lock and not the reaper, you have converted a data race into an outage with a longer time to detection.

Idempotency is the whole game

Every job in this platform runs more than once over the same data — by retry, by backfill, by reprocessing after a model fix. Four mechanisms did the work:

MechanismProblem it solves
Record hash stored with the rowA generic "update everything that changed" job can skip rows whose content is identical, which makes full-fleet re-syncs cheap
Unique index on the natural key (org, repo, number)Duplicate inserts fail loudly instead of silently doubling somebody's metrics
Deduplication jobs per entityCleans up what got in before the constraint existed — and something always did
Surrogate keys instead of provider identifiersWhen a repository is migrated between source-control instances its provider id changes; a surrogate key keeps history continuous

That last one deserves emphasis because it looks like pedantry until it isn't. We keyed some entities on the provider's identifiers, and then the company migrated to a different source-control instance. Identifiers changed. History fractured, and the repair involved not just a schema change but a series of careful model changes downstream to stitch two eras together. Any identifier owned by a third party is a foreign key into someone else's roadmap.

Reconciliation: assume the pipeline is lying

We ran scheduled checks comparing the operational database with the warehouse, per entity, per day, and alerted on divergence. This is the single highest-value job in any ETL platform and it is almost always the last one built, because it produces no features — it only tells you your features are wrong.

Alongside it, backfills became a first-class concept rather than a script somebody ran once: a job type with a date range, a concurrency setting, checkpointing and a dry run. We had backfills for missing records, for corrected metadata, for a new column, for a bug in a converter. Treating them as infrastructure instead of incidents is what makes a data model safe to change.

Making it fast: what worked and what didn't

Three rounds of performance work, with an honest score.

Parallelism with a configurable ceiling — worked. Per-repository processing, per-record updates, object storage writes and summary backfills all became parallel with a concurrency knob. The knob is the important half: the right concurrency is a function of the source's rate limits and the warehouse's tolerance, and both change.

Virtual threads — partially reverted. We upgraded jobs to a runtime with virtual threads and converted the I/O-heavy paths. Some of it was a clear win. Some of it we rolled back after finding problems, and the lasting fix was to keep an explicit semaphore around the work rather than assume cheap threads mean unbounded concurrency is fine. Virtual threads remove the cost of a blocked thread; they do not remove the downstream service's opinion about how many concurrent requests it wants.

Distributed batch processing — worked, once the framework fit. Some jobs simply do not fit on one machine: reprocessing every file of every pull request in the company's history, for instance. Those moved onto a MapReduce-style distributed framework. The lesson was less about the framework and more about the threshold: single-machine jobs with a concurrency knob get you remarkably far, and the moment to move is when the job's runtime stops fitting in the window between two runs of itself.

Two smaller ones that paid off immediately: giving the platform its own warehouse compute rather than sharing a busy one, and replacing plain caches in the read path with an asynchronous refreshing cache plus a pre-load at startup, so an expiring entry never makes a user wait for a slow query. Pre-loading took around twenty minutes to warm everything, which is fine when the alternative is a user watching a spinner.

The modelling layer is where the domain lives

The transformation layer — SQL models, version-controlled, tested, built on the warehouse — is where raw events become concepts: review cycle time, lead time, deployed changes, per-team rollups.

The hardest problems there were not SQL. They were identity and time:

  • Which team did this person belong to at the time? Attributing last quarter's work to this quarter's org chart produces numbers that are wrong in a way nobody can see. Temporal lookups against team-membership history are the fix, and they are a lot of work.
  • Which team does this repository belong to when the author belongs to several? We resolved it through repository ownership rather than author membership, which is more stable and more defensible.
  • Who is this, actually? Accounts get renamed and deleted; migrations leave suffixes on usernames; a deleted account's contributions appear under a placeholder. We stripped migration suffixes, mapped public accounts to internal identities, and attributed orphaned changes to the person with the most commits on them. Every one of those is a judgement call that belongs in a documented model, not in an application query where nobody will find it.
The principle

In a metrics platform, the modelling layer is the product. The number a leader sees is not "the data" — it is the output of a dozen decisions about identity, time and attribution. Keeping those decisions in reviewed, tested, version-controlled models is the only way the answer to "why is this number what it is" stays answerable.

Part 2 — From Charts to Narratives

The charts worked. Teams saw things about themselves they could not see before. And still, the most common feedback was a variant of: fine, but what does it mean? A chart of review latency does not tell a manager that an engineer spent the quarter unblocking three other teams through a migration nobody scheduled.

So we asked a different question: instead of only showing engineering activity, could we describe it — in prose, faithful to the data? It started as a hackathon pitch, it was picked as one of the three best projects, and then came the part that decides whether an idea is real: putting it into production for everyone.

What follows is the short version. The engineering of those agents — paginated tools instead of stuffed context, an evaluation harness with an LLM judge scoring citations, automated prompt evolution, and per-step model economics — has its own post.

Architecture: one agent per kind of contribution

The naive version — "here is everything this person did, write a summary" — fails for boring reasons. Context windows, cost, and the fact that different contribution types need different reasoning. Reviewing forty pull requests is a different kind of contribution from authoring three, and both are different from a month of answering questions in a support channel.

So: a separate agent per contribution type — authored changes, reviews, issues, support threads — each with its own prompt and its own notion of what matters. Each one summarizes hierarchically:

  1. Fetch the person's contributions for the period from the warehouse.
  2. Group them by theme rather than by date — because the unit a human recognizes is "the migration", not "the fourteenth of March".
  3. Summarize each theme from its own items.
  4. Summarize the themes into the top-level narrative.

That hierarchy is what makes the output readable. A flat list of forty changes summarized in one pass produces a list of forty changes with adjectives. Grouping first produces something that reads like a colleague describing the quarter.

The retry logic, counters and shared plumbing were factored out into common infrastructure early, once we had three agents. Model calls fail, rate-limit and occasionally return something unparseable; every agent needs the same handling, and three copies of it drift within a month.

The synchronous version had to die

The first implementation generated a summary inside the request that asked for it. That works in a demo and fails in production for a reason that has nothing to do with LLMs: the work takes longer than any reasonable request timeout, and doing it inline means a retry re-runs the whole expensive thing.

The production shape:

  • A request creates a row in a summaries table in a pending state and returns immediately.
  • Generation is enqueued on the task queue, where retries, concurrency and backoff already exist.
  • A worker generates, then writes the result back to the row.
  • The client polls; the UI shows a pending state instead of a spinner that might be a dead request.

This is an ordinary asynchronous job pattern, and that is the point. The novel part of an LLM feature is the prompt, not the plumbing — and teams reliably get this backwards, spending weeks on prompt engineering while the request-response shape quietly guarantees the feature cannot scale.

Prompts as code, with rules

Three decisions I would repeat.

Prompts live in templates, not in string concatenation. Moving them into a template engine made them reviewable, diffable and editable without a code change in five places.

Refer to people by username, never with pronouns. This started as a correctness rule — the model has no way to know anyone's pronouns, and guessing from a name is a coin flip that misgenders real colleagues — and it turned out to also make the prose better: it forced factual, attributable sentences rather than narrative flourish.

Detail level is an input, not a personality. Different readers want different lengths, so verbosity is configurable and items are sorted by relevance before summarization, so a shorter summary is the important subset rather than an arbitrary truncation.

Access control is a feature of the summary, not a wrapper around it

The moment you generate prose about individuals, permissions stop being infrastructure and become product. Who can read a summary about a person? The person. Their manager. Their manager's manager? An admin doing support? What about an impersonation session for debugging — does the summary render, and is that logged?

We built team-level authorization, a permissions endpoint the frontend uses to decide what to even offer, restricted group visibility, explicit rules for subordinates, and impersonation for support with tests covering it end to end. The rule of thumb that emerged: every permission question must be answered at generation time and again at read time, because the org chart moves and a summary generated when someone was your report should not remain readable after they are not.

The other agent: where did the engineering time go?

A related agent estimated how engineering effort distributed across product features, combining calendar availability with contribution data, rolled up per team and reviewable by the people it described. Useful for planning and for the finance-adjacent question of what was built.

The design decision that made it defensible: the estimate is reviewable and editable by the team, not an authoritative output. An estimate a human can correct is a conversation starter. The same number presented as fact is a thing people learn to game or resent.

The scar, restated because it is the most important part

Scar

With the chart product, some managers started using our numbers in performance reviews. Nobody asked us; nothing in the product prevented it. We had shipped something powerful without deciding what it was not for — and declining to make that decision does not mean it goes unmade. It means your users make it for you.

Narratives raise the stakes. A chart is obviously partial; a fluent paragraph about a person reads as a judgement even when every sentence is sourced. That is why the constraints above are not decoration: username-only attribution, every claim traceable to a linked contribution, the subject able to read their own summary, permissions enforced at both generation and read time, estimates editable by the people they describe. The guard rails are the product.

What made it worth doing anyway: the summaries genuinely surfaced work that was invisible to metrics. Review work, unblocking other teams, the migration that shows up as no features shipped. Some of the most respected engineers in the company wrote to us unprompted to say the narratives described their work accurately — which is the only quality bar that matters for a system like this, because the failure mode is not "it is wrong", it is "it is plausible and wrong".

Key Takeaways

  1. Land raw records in object storage and treat the warehouse as derived. Reprocessing, schema changes and disputes all become tractable.
  2. Batch at the natural grain of the source. One file per record breaks ingestion and makes backfills pathological.
  3. The key prefix is your only index. Entity and date, in that order, because that is how every reprocessing job is scoped.
  4. If you build a lock, build the reaper. A lock held by a dead process converts a data race into a silent week-long outage.
  5. Idempotency by construction: record hashes, unique natural keys, dedup jobs, and surrogate keys instead of a third party's identifiers.
  6. Reconcile the warehouse against the source on a schedule. It is the highest-value job and always the last one built.
  7. Make backfills infrastructure, not incidents. Date range, concurrency, checkpoints, dry run.
  8. Concurrency needs a knob and a ceiling — virtual threads remove the cost of blocking, not the downstream service's limits.
  9. Move to distributed batch when a job stops fitting between two runs of itself, not before.
  10. In a metrics platform, the modelling layer is the product. Identity and time decisions belong in reviewed models, not in application queries.
  11. Attribute to the team someone was on at the time. Anything else is wrong in a way nobody can see.
  12. One agent per contribution type, summarizing hierarchically by theme. Flat summarization produces a list with adjectives.
  13. LLM features are asynchronous jobs. Pending row, queue, worker, poll. The plumbing is where scaling is won or lost.
  14. Prompts are code: templated, reviewed, with explicit rules — usernames not pronouns, configurable detail, relevance-sorted input.
  15. Enforce permissions at generation time and at read time. The org chart moves after the text is written.
  16. Decide what your product is not for, and build that decision in. Otherwise your users decide it for you, in a performance review.
