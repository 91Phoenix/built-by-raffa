The Build Container Is Your Softest Target: Locking Down CI Without Breaking It

September 2026 · 17 min read

A build container runs arbitrary code, written by anyone with commit access, with credentials attached, on your network. That is not a vulnerability — that is the product. CI exists to execute the code people write. Every hardening decision has to start from accepting that and asking a narrower question: what can that code reach, and what can it take with it?

This post covers the hardening work we did on an in-house CI platform: network lockdown of build containers, secrets that builds can use without the build being trusted, catching typosquatted dependencies at the moment the build system learns about them, and the source-control integration surface around all of it. Anonymized — no employer, no internal service names; the third-party technologies named are public ones anybody can use. Every control here is defensive and generic.

The Threat Model, Stated Plainly

Four things a build container can do that you probably do not want:

CapabilityConcrete abuseControl
Arbitrary outbound networkExfiltrate source or secrets to any host; pull a payload from anywhereDefault-deny egress with an allowlist computed per build
Ambient credentialsA build for repo A uses a token that grants access to repo B's secretsSecret access gated on the identity of the repository being built
Arbitrary dependenciesA typosquatted package name pulls hostile code into the artifactValidate the resolved dependency set where the system already parses it
Privileged executionEscape the container, tamper with the host or the daemonRemove privileged commands; unprivileged nested containers; mediate the residue through a policy layer

Everything below is one of those four rows.

Control 1 — Default-Deny Egress, Computed Per Build

The hardest part of restricting build network access is that builds legitimately need a lot of network. They pull dependencies from internal mirrors and public registries. They clone from source control. They upload artifacts to object storage. They call the build system's own APIs. Block too much and every build in the company fails; block too little and you have built a compliance checkbox.

The design we landed on separates deciding from enforcing:

Details that made it workable:

  • Pull the ranges from the source of truth, filtered. Cloud provider IP ranges are published, and they are enormous. Filtering by service and region turns "all of the cloud" into a list with a defensible justification for each entry.
  • Allow domains as well as subnets, and resolve them yourself. Some dependencies only exist behind names whose addresses move. That means DNS resolution in the path of every build launch — so resolve in parallel, and cache with a refresh-after-write policy rather than expire-after-write. The difference matters: refresh-after-write serves the slightly stale value while refreshing in the background, so a slow resolver never stalls a build launch.
  • Ports are part of the policy. An allowlisted subnet on every port is a wider hole than people picture.
  • Roll out in phases. A percentage, then repositories, then everything, with the ability to fall back instantly. A network control that fails closed has the same user experience as an outage.

Where it ended up: names instead of address ranges

That first design is the one I described because it is the one you will build first, and it is worth understanding why it does not survive contact with time.

Enumerating IP ranges is a losing race. Cloud providers publish their ranges and then change them; a registry moves behind a different CDN; a service you allowlisted by address adds a region. The allowlist grows into thousands of CIDR blocks that nobody can review, nobody can justify entry by entry, and that are simultaneously too broad (an entire provider's range to reach one service) and too narrow (the one address that rotated last night and broke every build in the company).

So the policy moved up a layer. Instead of chasing addresses, it came to be expressed as:

  • Netmasks only where the target really is a network — internal subnets, the cluster, the artifact storage endpoints. These are stable, ours, and genuinely address-shaped.
  • Names, including whole subdomain trees, for everything external. Allow the registry's domain and its subdomains rather than the addresses it happens to resolve to today. The policy then reads like the intent it encodes: builds may reach this package registry, not builds may reach these 214 prefixes, reason unknown, added by someone in 2022.

The gains are mostly human. A name-based rule is reviewable — a person can look at an entry and say whether it should exist — and it stops churning every time a provider reshuffles its address space. Fewer emergency widenings means fewer permanent ones, because every allowlist entry added during an incident is an entry nobody removes.

The trade-off is that names are not enforced by the same mechanism as addresses. A packet filter matches addresses; matching a name means enforcing at a layer that can see it — a proxy in the path, DNS-level control, or SNI inspection — and pinning what your resolver is allowed to return so that a name cannot be pointed at somewhere it should not go. That is more moving parts than a firewall rule. It is also the only version of the control that a human can still audit two years later, which is what decides whether a control is real or merely deployed.

The test is the control

The part I would insist on anywhere: we tested the firewall rules for real, not mocked. The acceptance test for the executor actually applies the rules and verifies the effect. And a dedicated smoke-test build does the only end-to-end check that means anything — it tries to reach a domain that is not on the allowlist, and the test passes only if the attempt fails.

Mocking a security control tests that you called a function. The whole value of the control is what happens in the kernel afterwards.

The principle

If a control's enforcement is mocked in tests, the control is documentation. Network policy, permission checks and sandboxing must be verified by observing the blocked behaviour, in an environment shaped like production. Everything else is a unit test of your own optimism.

Control 2 — Secrets a Build Can Use Without Trusting the Build

Builds need secrets: credentials to publish artifacts, tokens for integration tests, signing keys. The naive approach bakes them into the image or the executor environment, which means every build of every repository has every secret. One compromised or merely curious repository, and it is all gone.

What we did instead: a small step that runs before the build command and fetches secrets from the secret manager into the build's environment file — but only after asking the build system whether this repository is allowed to have this secret. The identity being authorized is the repository under build, not the container, not the user, not the image.

Three properties that fall out of that ordering:

  1. The secret lands in the build's environment, so the build never learns how to talk to the secret manager itself.
  2. Authorization is centralized: the permission lives with the build system, which is the only component that knows what is being built and for whom.
  3. Rotation is an operation on one store, not an image rebuild. We rotated shared artifact credentials more than once, and the pain was proportional to how many copies existed — which is the argument for having as few as possible.

I would add one caveat learned the hard way: a secret written into a build's environment is available to everything the build runs, including its dependencies' build scripts. Scoping which secrets a repository may request is the only real boundary. "The build is trusted because the repo is ours" is not a boundary — it is the assumption every supply-chain incident starts from.

Control 3 — Catch Typosquats Where the Graph Is Already Parsed

Dependency confusion and typosquatting attacks work because a package name that looks right is trusted by everyone downstream. The usual answer is a scanner somewhere in the pipeline. The better answer, if you own the build system, is to check at the point where the system already knows the full dependency set.

Our build system parsed every module's build configuration to discover modules and their dependencies — it has to, to schedule anything. That parse is the ideal integration point: after discovery, the dependency set goes to a validator service, and anything suspicious comes back as a build processing issue attached to the module.

Why that placement is the right one:

  • No new parsing. A separate scanner has to re-derive the dependency graph, and will disagree with the build system eventually. Disagreement between two parsers of the same file is a permanent source of false positives that trains people to ignore the tool.
  • It reuses an existing feedback channel. Build processing issues were already a thing engineers saw and understood. A finding appears where they already look, without a new dashboard.
  • The validator gets the whole fleet's data. A background job pushed module data from a read replica to the validator, so it can reason about what is normal across all repositories rather than judging one dependency list in isolation. Knowing that 900 modules use a package and one uses a name that differs by a character is exactly the signal that catches a typosquat.

The detection itself was replaced more than once after I wrote the first integration — edit-distance heuristics give way to better signals, internal mirrors and namespace reservation close off whole categories, and the ecosystem's own tooling improves. That churn is the normal state of this control, and the wrong lesson to draw from it is that the specific check matters.

What mattered was that reducing supply-chain exposure stayed a standing effort rather than a project with an end date: a stable integration point in the build system where any new check can be plugged in, a feedback channel engineers already read, and someone whose job includes asking every few months what the current attack shape is. Dependency confusion, compromised maintainer accounts, malicious post-install scripts and poisoned build images are different attacks that arrive in waves; a platform that made room for the next check outlives any individual detector you write.

Control 4 — The Source-Control Integration Surface

A build system's other soft edge is the integration with source control: webhooks arriving from outside, API tokens going out, and a lot of implicit trust in payloads.

Do not build commits from organizations you do not recognize. This sounds absurd until you look at how webhook routing works in a large installation with public and internal instances. We started ignoring commits from unknown organizations outright, and added acceptance tests covering webhook security — because the test that the system refuses something is the one that regresses silently.

Treat API rate limits as a capacity resource. Source-control API tokens have quotas, and a build system is an aggressive consumer. Two changes made the difference: distributing calls round-robin across several API identities, and making the worst-behaved background job dramatically less greedy — removing its multithreading, adding caching, and rate-limiting it. A job that finishes in twenty minutes instead of five, without starving interactive builds of quota, is the better job. We also alerted on token usage at elevated and critical thresholds, so exhaustion became a warning rather than a morning of unexplained failures.

Detect provider maintenance and stop pretending. A health checker probed the source-control instances and marked them unhealthy when it detected maintenance responses. A maintenance mode then gated event processing — selectively, since an outage of the internal instance and an outage of the public one affect different builds. Afterwards, jobs cleaned up the build processing issues the outage had produced, because nothing erodes trust in a signal faster than stale errors from an incident that ended yesterday.

The through-line: external dependencies fail in ways your code will interpret as data. An HTML maintenance page parsed as an API response, a rate-limit error treated as "no results", an event from an organization you have never heard of. Every one of those is an input-validation problem wearing an infrastructure costume.

Control 5 — Remove the Privileges Nobody Needs, and Mediate the Ones They Do

The least glamorous and most effective category: taking capabilities away.

The platform had supported privileged build commands — an escape hatch from an earlier era for builds that needed to do host-level things. We removed the references, then the feature, along with the tests that proved it worked. Similarly, a legacy build type that required a container daemon running in a mode incompatible with the newer sidecar arrangement was retired rather than accommodated.

Both removals were possible only because someone went and checked who was still using them. That is the actual work in deprecating a capability: not the delete, the census. And it is the work that gets skipped, which is why platforms accumulate escape hatches whose only remaining user is the incident that will exploit them.

But builds do build containers

The census never gets to zero, and the reason is structural: a large share of builds produce container images. Building an image inside a container is the nested-container problem, and the historical answer — run the build container privileged, or hand it the host's container socket — is not a sandbox at all. A build with the host socket can start a container mounting the host root filesystem. That is not an escape; it is the documented behaviour of the thing you gave it.

So the direction of travel was: make the inner daemon real, and make its privilege fake. The pieces the ecosystem now gives you, in rough order of how much they buy:

  • Nested containers without host privilege. Container runtimes exist specifically to make Docker-in-Docker work unprivileged — Sysbox is the best-known — by placing the workload in its own user namespace and emulating the parts of procfs/sysfs the inner daemon expects. Root inside the build is a namespaced root mapped to an unprivileged user outside it. The build can run its daemon and build its images; the identity it holds on the host is nobody.
  • Rootless daemons and daemonless image builders for the cases that do not need a full inner Docker. If an image build is all you want, a builder that produces images without a privileged daemon at all removes the question rather than answering it.
  • Kernel-level confinement underneath both — seccomp and mandatory-access-control profiles, dropped capabilities, no new privileges — so that even the namespaced root cannot reach for syscalls the build has no business making.

Which leaves the residue: a small set of operations that genuinely require privilege and genuinely have to be allowed for specific builds. The answer there is not a per-build exception; it is a mediator. The daemon's API sits behind an authorization layer — Docker supports authorization plugins for exactly this, and in a Kubernetes-based fleet the equivalent is an admission controller with a policy engine — which sees every request and decides, against policy, whether this repository may perform that operation.

The shape that matters

Every privileged operation goes through a component whose only job is to say yes or no, with the policy written down somewhere reviewable, and every decision logged. The alternative — a flag on a build config that means "this one is allowed to do dangerous things" — is a policy too, but one that is scattered across thousands of repositories, has no audit trail, and only the person who added it knows why it is there.

The property I would hold onto if I had to keep one: a build that wants privilege must ask something that can refuse. Not a flag it sets itself, not a socket it was handed, not a capability it inherited. A request, to a mediator, against a written policy, recorded.

What I Would Do Differently

Three things.

Build the allowlist observability before the enforcement. We rolled out in phases, which was right, but the fastest way to size the blast radius would have been a logging-only mode that records what would have been blocked, across the whole fleet, for a week. Phased enforcement discovers the exceptions one angry team at a time; shadow mode discovers all of them at once and lets you fix them before anyone notices.

Treat every allowlist entry as expiring. Entries get added during incidents and stay forever. An allowlist with a required justification and a review date is a slightly annoying process that prevents a permanently widening hole.

Decide the secret-scoping model before you make secrets available at all. We got the authorization check right — permission verified against the repository being built — but the granularity question ("which secrets may this repo request, and who approves that") deserved to be answered first, because it is much harder to tighten a scope people already depend on than to widen one.

Key Takeaways

  1. Start from what the container can reach and take, not from a checklist. Network, credentials, dependencies, privileges — four rows, four controls.
  2. Separate policy from enforcement. A service computes the allowlist; the executor only applies it. Policy changes are a deploy, not a fleet-wide image rebuild.
  3. Allowlists need ports and names, not just subnets — and names mean DNS in the launch path, so resolve in parallel and refresh caches in the background.
  4. Chasing IP ranges is a losing race; express external policy as names and subdomain trees. Netmasks for the networks that are genuinely yours. A rule a human can still justify in two years is the only kind that stays real.
  5. Never mock a security control in its own test. Apply the real rules and assert the traffic is blocked.
  6. Authorize secrets against the identity being built, and hand the secret to the build rather than teaching the build to fetch it.
  7. Rotation cost is proportional to copies. Fewer copies is a security property and an operational one.
  8. Validate dependencies where they are already parsed. A second parser will disagree with the first, and disagreement trains people to ignore findings.
  9. Report findings through a channel engineers already read. A new dashboard is a new thing to ignore.
  10. Fleet-wide context is what catches a typosquat. One repository's dependency list in isolation tells you nothing.
  11. Build the integration point, not the detector. The specific check will be replaced; supply-chain work is a standing effort, and the platform's job is to make room for the next one.
  12. Reject input from unrecognized sources, and test the rejection. Refusals regress silently.
  13. Rate limits are capacity. Distribute identities, throttle the greedy background job, alert before exhaustion.
  14. External outages arrive as malformed data. Health-check providers, gate processing during maintenance, and clean up the errors afterwards.
  15. Deprecating a capability is a census, not a delete. The escape hatch nobody uses is the one that gets used against you.
  16. Nested container builds do not need host privilege. A user-namespaced runtime built for unprivileged Docker-in-Docker, or a daemonless image builder, plus seccomp and capability confinement underneath.
  17. A build that wants privilege must ask something that can refuse. Route the residue through an authorization plugin or admission policy — written policy, per repository, every decision logged — never a flag the build sets on itself.
  18. Run new controls in shadow mode first. Discover every exception in a week, instead of one angry team at a time.
