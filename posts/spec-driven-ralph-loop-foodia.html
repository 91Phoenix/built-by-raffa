A €7,200 Paella: Spec-Driven Development, a Ralph Loop, and the Bugs Neither Caught

September 2026 · 26 min read

The project is called Foodia. The name is bad. I typed it into gh repo create on a Tuesday, told myself I would fix it later, and then spent four months and 340 commits not fixing it. Nothing else about the project was decided that casually, which is roughly the point of this post: everything downstream of the name went through a written specification, a domain glossary, architecture decision records, and an orchestration loop that turns GitHub issues into reviewed pull requests without me typing the code. The name is the one artifact with no spec behind it.

Foodia is a meal-planning platform: 841 Italian recipes and 891 ingredient encyclopedia entries in Postgres, a Django REST backend, a React frontend, and an LLM agent with eighteen tools that plans your week, tracks your pantry, reads your grocery receipt and tells you what it all costs. The scraper that filled that database was the subject of an earlier post. This one is about what got built on top, how it got built, and what I found when I pulled the repo onto a clean machine and actually looked at the numbers it produces.

One thing to be clear about before anything else, because it changes how you should read the rest: I have not read most of this code. Foodia is not a codebase I maintain. It is an experiment in running a software factory — writing the specification, the glossary, the standards and the tickets, then letting a loop of agents produce the implementation, review it, fix it and hand me a pull request. My job in that arrangement is the input side and the merge button. For long stretches, the only thing I read about a feature was the ticket I wrote and the PR description an agent wrote back.

That is the experiment, and it mostly worked: thirty pull requests written, reviewed and fixed by agents, merged by me. It also means the section near the end is not a retrospective. It is me reading my own repository for the first time, and finding a paella priced at €7,208 — which sailed through every layer of the process, because each layer was checking whether the code did what the spec said, and the spec never said anything about what a pistil of saffron weighs.

Part 1 — The Spec Layer

The technique, which I picked up from Matt Pocock's writing on driving agents from specifications rather than chat, is that the durable artifact of a feature is not the code. It is the sentence that defines the term. So the repo root holds CONTEXT.md: a glossary where every domain concept gets a definition, a storage location, and — the part that does the real work — a list of words you are not allowed to use for it.

**Batch Cooking (Batch Group)**:
Multiple MealPlan entries sharing the same `batch_group` UUID. A single
cooking session produces food consumed over multiple days (e.g. ciambellone
baked Monday covers breakfast Mon-Fri). The originating entry is marked
`is_batch_origin: true`.
_Avoid_: leftovers (loaded term), meal prep

That _Avoid_ line is the highest-leverage text in the repository. An agent handed "implement leftovers support" will invent a Leftover model with a foreign key to MealPlan, and it will be defensible, and it will be wrong — because the concept already exists as a UUID shared across rows. Naming the rejected words prevents the parallel vocabulary from ever being born. There are eighteen such entries, covering batch cooking, dietary splits, shelf life, seasonality, per-user price overrides, receipt scans and baseline cost.

Underneath the glossary sits an example dialogue — a scripted conversation between "Dev" and "Domain Expert" that walks the hard cases:

Dev: And the ciambellone baked Monday for the whole week?

Domain Expert: One entry on Monday is is_batch_origin: true with batch_group: abc-123. Tuesday through Friday have entries with the same batch_group referencing the same recipe. The planner knows not to schedule new breakfasts, and the shopping list buys ingredients only once.

This is the part I would skip if I were in a hurry, and the part that pays. A definition tells an agent what a field is called. A dialogue tells it what the system is supposed to do when a household of four contains one vegetarian and lunch is a primo plus a secondo. That case — four MealPlan rows on one date and meal type — is the reason MealPlan has no unique constraint on (user, date, meal_type), and the reason is written down where the next agent will read it.

Decisions that survive a debate go to docs/adr/, with the rejected options kept:

# UserIngredientPrice as separate model, not on IngredientStock

1. **`unit_price` on `IngredientStock`** — Dies when stock is consumed via
   `auto_remove_stocks`. User would lose their price override every time
   they eat.
2. **`unit_price` on `IngredientInfo`** — System-wide, not per-user. Fails
   the core requirement: different users pay different prices.
3. **`UserIngredientPrice` as separate model** — Chosen. Survives pantry
   depletion.

Option 1 is exactly what an agent optimising for the smallest diff would pick. It is one field on an existing model, it passes every test you would think to write, and it silently deletes the user's data the first time the pantry auto-depletes. The ADR is a tripwire in front of that.

Scar

Both agent prompts open with "Read AGENTS.md at repo root for project conventions." AGENTS.md has never existed in this repository — not in the working tree, not in any of the 340 commits. Every agent that ran for a month was instructed to consult a file it could not find, and none of them complained, because a missing file reads to an agent as an empty one. Meanwhile the conventions file that does exist, .sandcastle/CODING_STANDARDS.md, contains the line "Frontend: Vue 3 Composition API, single-file components". The frontend is React 18 with Create React App and has been since the first commit. The spec layer needs its own tests, and I did not write any.

Part 2 — The Loop

A Ralph loop, in the original sense: one prompt, one sandbox, run it again until there is nothing left to do. The shape of the iteration is the part I care about — plan centrally, execute in parallel, review before a human ever looks — and it survived a change of runtime underneath it. The first version, which is the one still committed to the repo as .sandcastle/main.mts, was 140 lines of TypeScript on top of an off-the-shelf sandbox library; I tried it, kept the shape, and replaced the machinery with my own runner. The pull requests below came out of the replacement.

Because the prototype is what the repository contains, it is what I can quote, and the design it encodes is the design that shipped.

Phase 1: the planner is paranoid on purpose

The planner reads every open issue labelled ready-for-agent and decides which ones can be worked right now without waiting on another. The blocking rules are deliberately broad — an issue is blocked if it references another, if it needs a model or utility another introduces, if it touches the same files, or if it depends on an API shape another will establish:

Be strict: if there's any reasonable doubt, mark it as blocked. Only mark an
issue as unblocked when it can be fully implemented independently with zero
waiting on other issues.

Bias toward blocked is the right default, and it took one painful afternoon of merge conflicts to believe it. Two agents adding a field to the same model produce two migrations with the same parent, and resolving that costs more human attention than running the second issue in the next iteration would have. The branch name is pinned to sandcastle/issue-{id} precisely so that re-planning is idempotent: the same issue always resolves to the same branch, so a crashed iteration resumes instead of forking.

Output is a JSON object inside <plan> tags, parsed against a schema. If the tag is absent the loop breaks rather than guessing — the one place in the whole system where I preferred a hard stop to a heuristic.

Phase 2 and 3: implement, then review, per issue, in parallel

Every unblocked issue gets its own container on its own branch, and inside it an implementer runs to completion before a reviewer looks at the result. Three properties of that fan-out earned their place, and they are the ones I carried from the prototype into my own runner.

Settle, do not race. One agent hitting an unfixable test must not cancel the other four, so the parallel section waits for every branch to finish or fail independently rather than aborting on the first rejection. Kill on silence, not on crash. A stuck agent is the expensive failure mode — a crashed one costs you nothing but a log line — and five minutes with no output is a reliable signal that a session is never coming back. Use commits as the completion test. An issue that produced no commit is not a failure; it is the agent reading an under-specified ticket and stopping, which the implement prompt explicitly tells it to do. Branching on "were there commits" is how the loop tells those apart without parsing prose, and only branches with commits go on to be reviewed.

The implementer's contract is strict TDD (write the failing test first, per sub-step), then the full local suite, then ruff, then a frontend build, then a PR whose body must contain a manual test plan for a human, then poll CI until green. The reviewer then inspects the diff for correctness, test coverage, security, Django-specific traps (missing migrations, N+1 queries) and style, posts a review comment whether or not it found anything, fixes what it found, pushes, waits for CI and re-reviews until clean. It is required to name its own model in the comment, which is how I can tell a bad review from a bad reviewer:

## Review (deepseek/deepseek-v4-pro)
**Findings**: <summary>
**CI status**: <green/red/yellow>
**Verdict**: <✅ / ❌ / ⌛>

The one thing the loop is forbidden to do is merge. Thirty pull requests came out of sandcastle/issue-* branches; I merged all thirty by hand, against 43 merged from branches I wrote myself. Eleven commits in the history are the reviewer fixing its own implementer's work — Address review comments: unit validation in agent tool, fix disambiguation message leak, rename/add tests is a real commit message, and the reviewer found that leak, not me.

Throughput was lumpy in exactly the way you would expect from a serialised planner: ten of the thirty PRs merged on a single day, 4 June, then long gaps while I read them.

Scar

The harness under the first version took nine commits in one day to stabilise, and none of them were about prompts: use explicit sudo, not sandcastle's sudo prefix, chain dependent hooks to avoid parallel race, stabilize planner hooks, fix virtiofs mounts, bake pip deps, rebuild image with PostgreSQL server, add build-image.sh with host UID/GID auto-detection. An agent harness is not a prompt with a wrapper. It is a build of a Linux image with a database server, a compiled pgvector, a GitHub CLI and a UID that matches the host's so the mounted workspace is writable. Budget for that as infrastructure, because that is what it is.

One nice consequence of doing it properly: each sandbox boots Postgres, creates the vector extension, runs migrate, and loads the committed dump.json fixture before the agent starts. Every agent gets 841 real recipes to test against, isolated from every other agent. That hook is four lines of shell and it is the difference between tests that pass and tests that mean something.

Part 3 — The Features Worth the Trouble

Replacing vector RAG with a wiki the agent can walk

The original design used pgvector embeddings for recipe retrieval, and it was mediocre at the queries that actually matter. "Something vegetarian, cheap, that keeps for three days" is not a similarity problem; it is three predicates. Cosine distance will happily hand you a delicious €40 roast.

So the knowledge layer became a generated wiki: one markdown file per recipe and per ingredient, with the structured facts in YAML frontmatter and the prose in the body.

---
title: "Cheesecake leggera"
category: "Dolci"
servings: 10
shelf_life_days: 5
prep_minutes: 30
calories_per_serving: 245
estimated_cost: 1206
dietary_tags:
  - vegetarian
ingredienti_structured: [{"name": "Biscotti secchi integrali", "unit": "g", "quantity": 180.0}, ...]
---

The agent gets three tools over that directory — list_wiki_index() for the entry point, read_wiki_file(path), and grep_wiki(pattern), which understands typed filters over the frontmatter and composes them with AND:

grep_wiki("dietary_tags:vegetarian AND calories_per_serving <= 400 AND shelf_life_days >= 3")

Generation is a Django management command, and the interesting flag is --with-rephrase, which is opt-in. Without it the command emits templated markdown from database rows and calls no model at all. On my laptop:

OperationResultTime
generate_llm_wiki (no rephrase)1,761 files, 7.9 MB1.1 s, zero LLM calls
3-predicate compound query196 recipes2.40 s
category:Dolci AND calories_per_serving <= 30057 recipes2.09 s

Rebuilding the entire knowledge base in about a second, for free, deterministically, is the property that makes this design worth defending. Embeddings cost money per document and go stale silently when a row changes; this corpus is a pure function of the database, so the recovery procedure for "the wiki is wrong" is to delete it.

The honest cost is on the read side. _grep_wiki_structured does os.walk over the whole tree, parses every file's YAML frontmatter, and evaluates the predicates in Python — an O(n) full-corpus scan per query, which is where those 2.4 seconds come from. The generator also writes an indexes/ tree that already has the answers pre-bucketed:

# Dietary
- [Vegetarian](vegetarian.md) (484)
- [Vegan](vegan.md) (95)
- [Gluten-Free](gluten-free.md) (283)
- [Low Calorie ≤400](low-cal.md) (304)

…and grep_wiki never consults them. The agent can reach them by reading INDEX.md and following a link, which is a very different thing from the tool being fast. At 1,761 files a scan is a rounding error against an LLM round trip. At 50,000 it is the whole latency budget, and the fix is already sitting in the repo unused.

The cost chain, and a receipt that is allowed to disagree with you

Cost resolution has a strict precedence: a per-user price override beats the system-wide catalogue price, which beats a regional heuristic. Every ingredient quantity is normalised toward kilograms, and an out-of-season ingredient carries a ×1.3 multiplier.

The design decision I am still happy with is what happens when you photograph a supermarket receipt. A vision model extracts the line items into ReceiptScan and ReceiptScanItem rows, and those real prices feed an "actual spend" line on the dashboard next to the estimate. What they explicitly do not do is update your saved price. From the glossary: "Does not auto-update UserIngredientPrice — user must explicitly accept." If you told the system pasta costs €1.20/kg and a receipt says €1.10, the system shows you both and shuts up. A system that silently rewrites a number the user typed is a system the user stops typing numbers into.

Medical language, deliberately forgotten

Users describe food restrictions in medical terms because that is how humans talk: "I'm coeliac", "lactose intolerant". Storing that means storing health data, with everything GDPR attaches to it. So free-text preferences pass through an LLM whose entire job is to translate clinical language into preference language before anything is written to the database, preserving intensity while dropping the diagnosis — an allergy becomes "I absolutely have to avoid", an intolerance becomes "I try to limit". The prompt is blunt about it:

REGOLA FONDAMENTALE: L'output NON deve MAI contenere riferimenti a:
- condizioni mediche, diagnosi, patologie
- reazioni del corpo, digestione, sintomi fisici
…
2. Non rivelare mai la presenza originale di termini medici.

Two things make this more than prompt theatre. The rephrasing is not logged, because a log of "what the user originally wrote" is exactly the record the feature exists to avoid creating. And when the model fails, the code falls back to storing the user's original text rather than dropping their input on the floor — a deliberate trade of strictness for not losing data, which is the sort of thing that belongs in an ADR and currently lives only in an except block.

Token accounting per user, per feature

Every model call is attributed: LLMUsageDaily holds prompt, completion and reasoning tokens keyed by (user, date, feature, model), with a price table in settings turning tokens into euros for an admin dashboard. Eleven features are enumerated, from chat to scan_receipt to generate_wiki. Two of the model entries are priced at (0, 0), so the vision calls report as free — which they are not. The accounting skeleton is right and one table needs numbers in it.

Part 4 — What Neither the Spec Nor the Loop Caught

Everything above is the part I would put in a talk: the specification, the loop, the features the two of them produced. Here is what happened when I finally cloned the repo onto a clean machine, seeded the database, started the app and looked at what it says.

This is the honest accounting of the experiment. Thirty agent-written pull requests, 703 tests, a glossary, an ADR trail and a reviewer that catches message leaks — and every single defect below was found in the first afternoon that a human ran the thing and read the output. Not one of them needed me to read the implementation, which is just as well, because I still have not.

1. The ingredient namespace is scraped text wearing a table

The master ingredient list is derived from raw recipe lines by one regex — cut the string at the first digit:

def extract_ingredient_name(raw):
    match = re.match(r'^(.+?)\s+\d+', raw)
    if match:
        return match.group(1).strip()
    return raw.strip()

On "Farina 00 200 g" that works. On anything where the quantity is expressed in words, or hidden in a parenthetical, it keeps the whole line. The result is 2,029 rows in a table called Ingredient:

Rows in IngredientCountExample
Starting with "Acqua"39Acqua mezzo bicchiere
Starting with "Uov"54Uova (1 intero e
Four words or longer638Vitellone 1 pezzo di reale

Thirty-nine kinds of water. A slice of them, in the order Postgres hands them back:

'acqua'                      # 'Acqua' is a second, separate row
'Acqua (alla temperatura di' # truncated mid-sentence
'acqua q'                    # "q.b." cut at the dot
'Acqua mezzo bicchiere'      # quantity in words, so the digit regex never fired
'Acqua minerale ghiacciata'
'Acqua o brodo di verdure'   # two ingredients, one row
'Acqua (variabile in base a quanto sia da bagnare il pane)'

One row is a truncated sentence about how wet the bread should be; one offers a choice between water and vegetable stock; several are the same water at a different temperature, and acqua and Acqua are two distinct rows because the uniqueness constraint is case-sensitive. The encyclopedia table, which is supposed to hold one entry per real-world ingredient, has six separate entries for cuts of veal and one called Uova 1 da. None of this is cosmetic, because the price lookup runs on these strings.

2. Substring matching turns a dictionary into a coin flip

Price resolution matches ingredient names by containment in either direction — short in target or target in short — and takes the first hit while iterating a dict. I measured what that means across every distinct ingredient name that appears in a recipe's structured list:

Distinct ingredient names in recipes1,181
Match exactly one price row638
Match more than one price row543
Match none0

For 46% of ingredients, which price you get depends on iteration order. The spreads are not subtle: acqua matches 19 rows ranging €0.30–€10.00/kg; sale matches 13 rows over €1–€20; manzo matches 15 rows over €2–€30. The worst is risotto allo zafferano freddo, which matches two rows spanning €2.00 and €15,000.00 per kilo — a factor of 7,500 decided by whichever key Python reaches first.

3. The generic unit weight, and the €7,200 paella

Recipe quantities arrive in Italian kitchen units, so there is a lookup table converting each to kilograms: a cucchiaio is 0.015 kg, a foglia is 0.001 kg, and the fallback — along with pz, "pieces" — is 0.08 kg. Eighty grams per piece is a fine guess for an egg or a lemon. The source line for the saffron in Paella alla valenciana is "Zafferano in pistilli 6": a quantity with no unit at all, so the parser supplies pz. Here is the cost breakdown, recomputed on my machine:

{'name': 'Zafferano in pistilli', 'quantity': 6.0, 'unit': 'pz', 'cost': 7200.0}
{'name': 'Coniglio a pezzi',     'quantity': 150.0, 'unit': 'g', 'cost': 1.35}
{'name': 'Pollo a pezzi',        'quantity': 150.0, 'unit': 'g', 'cost': 1.35}
{'name': "Olio extravergine d'oliva", 'quantity': 80.0, 'unit': 'g', 'cost': 1.2}

Six pistils of saffron × 0.08 kg × €15,000/kg = €7,200. Six pistils weigh roughly twelve milligrams and cost about eighteen cents. The recipe serves two, so the app is prepared to tell a user that dinner costs €3,604 a head. The number stored on the row disagrees with both: estimated_cost = 90108. Whatever wrote that is not what computes the estimate today, and nothing has reconciled them.

The reason this survived thirty agent reviews and every test I wrote is that it is almost never wrong. Across all 841 recipes, nine come out above €50 per serving:

recipes over 50 EUR per serving: 9 of 841
[(4500, 'Riso al salto'), (3604, 'Paella alla valenciana'), (100, 'Plumcake allo yogurt'),
 (100, 'Ossobuco alla milanese'), (100, 'Frolla Milano'), (99, 'Pan di Spagna')]

Nine out of 841 is 1.1%. A weekly plan of 28 meals came to €74, which looks completely plausible, and stays plausible right up to the week the planner picks a risotto with saffron in it. Every review question was "does this code do what the ticket said?" — and it does. Nobody asked "is €4,500 a sane price for fried rice", because that is a question about the world, and the loop has no eyes.

Scar

The seasonality multiplier never fires on this data: seasonality_months is empty on all 891 encyclopedia rows in the committed fixture. A ×1.3 adjustment implemented, tested, documented in the glossary, and dormant. Worth remembering next time a spec says a field is "populated by LLM during ingest" — that sentence describes an intention, not a column.

4. Frontmatter that looks precise and measures nothing

shelf_life_days is the field that makes "something that keeps until Thursday" answerable, and the wiki generator falls back to a per-category default when the recipe's own value is null:

CATEGORY_SHELF_LIFE_DEFAULTS = {'primi': 2, 'secondi': 3, 'antipasti': 3,
                                'contorni': 3, 'dolci': 5, 'colazione': 5}

Sensible. Except that on the shipped data, the number of recipes with a real, estimated shelf_life_days is zero out of 841. Every value in every wiki file is the category default. So grep_wiki("shelf_life_days >= 4") is not a shelf-life query at all — it is a slightly obfuscated way of asking "is this a dessert or a breakfast", and it returns a precise-looking number with a typed comparison operator to prove it. A default that is indistinguishable from a measurement is worse than a null, because null makes the agent ask.

5. A savoury pie for breakfast

I seeded a user, generated a week, and looked at what the planner actually served. Friday's breakfast: Torta rustica salata — rustic savoury pie. Saturday's: Torta salata ai carciofi — artichoke tart. Two lines explain it:

MEAL_CATEGORY_MAP = {'breakfast': ['dolci', 'antipasti', 'colazione'], ...}
BREAKFAST_KEYWORDS = [..., 'ciambell', 'muffin', 'pane', 'dolce', 'torta', ...]

Breakfast accepts the antipasti category, and 'torta' is a breakfast keyword because in Italian a torta is usually a cake. A torta salata is a quiche. The substring match cannot tell, and the word that disambiguates — salata — is sitting right there in the title being ignored. It is the same bug class as the scraper filing monkfish under fruit, in a different file, two months later. Substring classifiers do not get safer with practice; they get safer with a test per adversarial case, and I wrote those for the scraper and not for the planner.

6. A dashboard that cannot see the future

The spending dashboard showed €14.00 estimated for a user whose saved plan costs €74. Both numbers come from the same function. The difference is the window:

today = date_type.today()
cutoff = today - relativedelta(months=months)
plan = compute_weekly_plan_cost(request.user, cutoff, today, ...)

The window runs from twelve months ago to today, which is correct for receipts — you cannot scan a receipt you have not been given — and wrong for meal plans, which are the one thing in the system that exists to describe next week. Of 28 planned meals, 24 fall after today and are invisible; the €14 is Friday's four meals. A user's first act after generating a plan is to ask what it will cost, and the answer is off by 5× in the direction that makes the app look broken. Two date ranges got collapsed into one because they were both "the spending period", and the glossary never separated them.

7. The test that was green when it merged and rotted by the calendar

703 tests. One failure:

FAIL: test_user_drilldown_data (recipes.tests.test_analytics.AdminAnalyticsDataTestCase)
AssertionError: 0 != 2
Ran 703 tests in 136.265s
FAILED (failures=1)

The test writes two usage rows dated self.today, then calls the analytics endpoint with no date parameters. self.today is not today:

self.today = date(2026, 5, 31)

…and the endpoint, given no range, defaults to date.today() - timedelta(days=30) … date.today(). The fixture was inside the default window while the wall clock stayed within thirty days of 31 May, so the test passed, CI went green, the reviewer approved and I merged. It has been failing since the first of July, silently, for every developer and every agent that runs the suite. A hardcoded date plus a relative window is a time bomb with a fuse measured in weeks, and the one thing guaranteed not to notice is a process that only ever asks "is CI green right now".

Part 5 — Fixing It, and What It Looks Like Now

All of the above is fixed, in one branch, which is open as a pull request I have not merged. That is deliberate: the same rule the loop follows applies to me.

Two of the fixes were small. The rotten test's fixtures became relative to the clock. The spending window now runs to the last planned date instead of to today, so the estimate covers the plan rather than the one day of it that has already happened. Breakfast candidacy moved from title keywords to the recipe's category, because the keyword list could not be saved: with 'torta' admitting quiches, my first patch added an exclusion list, and the planner promptly served Panelle — fried chickpea fritters — on the strength of 'pane'. Sweet categories, 221 recipes, title words only allowed to rule a recipe out.

The data and cost fixes are the substantial ones, and they are three layers of the same problem:

  1. Canonicalise the names at ingest. A new module reduces a scraped line to the ingredient itself, and a management command rewrites and merges the rows that already exist, moving pantry entries, price overrides and receipt items onto the survivor. 2,029 ingredients became 1,093, and 891 encyclopedia entries became 849. Flour grades survive — Farina 00 200 g becomes Farina 00, not Farina — and real descriptors like Acqua minerale ghiacciata survive too, because the price lookup no longer needs them gone.
  2. Match on the head noun, not on a substring. A catalogue name applies only if it is the ingredient's opening words, longest prefix first, ties broken alphabetically. zafferano still prices Zafferano in pistilli; it no longer prices a risotto that merely mentions saffron, mela cannot reach melanzane, and no price depends on dict iteration order any more.
  3. Refuse to guess a weight you cannot afford to guess. Above €200/kg a generic unit gets no cost at all — the ingredient is reported with an explicit "unit weight unknown" instead of a number. Pistils got a real weight, bustina joined the generic units, and a bare count above 50 is read as grams, because "Gamberi 300" is 300 grams of prawns and not 300 prawns.

The paella that cost €7,208 now costs €7. Across all 841 recipes, nothing exceeds €50 per serving — the worst is €16, the median is €1.08. Fifty-two new tests pin each of these cases, one per failure above, and the suite is 755 green.

For the images there was no clean answer at first. media/ is gitignored and image_url is empty on every shipped row, and the source site's robots.txt disallows AI crawlers outright, so re-crawling is the operator's call and not something an agent should do on his behalf. What the branch does is stop the loss for next time — the loader now carries image_url through — and draw an honest placeholder per recipe: a flat colour, the dish name, the category, and the words immagine non disponibile. Nothing pretending to be a photograph.

Then we tried to actually run the crawler

The project owner ran the one command that should have fixed the images properly, as the site's own declared bot. It died immediately:

$ python run_crawler.py recipes
KeyError: 'Spider not found: giallo_recipes'

The spider is called giallo_recipes and it does exist. What does not exist is scrapy.cfg, which was never committed — so get_project_settings() returns Scrapy's defaults, SPIDER_MODULES is empty, and no spider can be discovered. The crawler has never been runnable from a clean clone. That is also the real reason the photographs were unrecoverable: the tool that would refetch them has never started.

Fixing that revealed the next one. Any use of the scrapy CLI — fetch, shell, list — failed on ITEM_PIPELINES naming ImageDownloadPipeline, a class that has never been in pipelines.py. run_crawler.py overrides that setting, which is precisely why nobody noticed.

With both fixed the crawl ran, reported success, and collected 56 recipes. The stats say why: request_depth_max: 1 — page one of each of the four categories, then nothing. The pagination selectors were written against markup the site no longer serves: it looks for a[rel="next"] and a.gz-page-link, while the page renders a.page, a.page.cur and an a.gz-arrow.next arrow, with pages as path segments (/ricette-cat/page2/Primi/). No error, no warning — the same silent-loss shape as the MAX_PAGES = 15 cap in the scraper post, three months later, in a different file.

Scar

And one of the six was mine. Placeholders live in Recipe.image like any other image, and both the crawler pipeline and download_images decided whether to fetch the real photo with if not recipe.image. Once my placeholders existed, that test was false for every recipe: the crawl set image_url on 56 rows and downloaded zero photographs. I had introduced exactly the bug class I had spent the afternoon writing about — a value that is indistinguishable from the thing it stands in for. There is now one definition of what counts as a photograph, in recipes/images.py, used by all three call sites.

With the selectors fixed, the crawl walks the whole of each category. It had found 3,549 recipes and downloaded 3,547 photographs when we stopped it early, still going. The database had 841. That number was never the site's catalogue: it was what fitted inside fifteen pages per category before the cap, and then what fitted in one page per category after the selectors broke.

The pipeline was red before any of this

The pull request went red on CI, and it took reading the run to see that nothing on the branch had caused it:

ModuleNotFoundError("No module named 'agno.models.metrics'")
TypeError: cannot pickle 'traceback' object

The workflow installs a hand-written package list instead of requirements.txt, so the agent framework was resolved fresh on every run and has since moved past the pinned <=2.6.11. The second line is the parallel test runner failing to serialise the first one, which is how the real error stayed invisible. The lint step would have failed next for the same reason: ruff installed unpinned and run with no config, and a later release widened its default rules from clean to 428 findings on untouched code.

A pin that CI ignores is not a pin. The workflow now installs requirements.txt, pins the linter, and states its rule set in a ruff.toml; --parallel is gone so a failing test can say which test it was; and the path filters no longer watch two files that do not exist while ignoring the Scrapy project, the dependency list and the crawler entry point.

What live API keys changed

Receipt scanning was pinned to a vision model the provider had retired, so every scan died on Invalid model and returned a 500 carrying the raw exception. DeepSeek does have vision, on deepseek-v4-flash-vision-exp — not in the /models listing, so it has to be named explicitly, and sending an image to the text model does not error, it silently ignores it ("But there is [Unsupported Image] placeholder. As AI, cannot see image", says the model's own reasoning trace). It is also a reasoning model: extracting twelve receipt lines spent 4,422 tokens thinking before emitting a character of JSON, so the code's max_tokens=1000 truncated every reply and made it look like a model that could not read receipts. With the budget raised it returns all twelve items and a total matching the receipt exactly.

And with the chat working, one more: asked what the week costs, the agent called show_spending, got back "no receipts found", and invented an answer — "siamo nell'ordine dei 100–140 €" — for a week the dashboard priced at €68 from the same database. The tool only ever looked at receipts. It leads with the plan estimate now, which is the number the question was about.

Here is the result, on the fixed branch, with real photographs and live keys: the recipe grid, a search, a recipe costed ingredient by ingredient, the week's plan, the spending dashboard comparing estimate against a scanned receipt, and the agent answering the cost question from the tool instead of from imagination.

Part 6 — Getting It Running, and the Bit That Cannot Be Recovered

The repo commits a 5.5 MB dump.json so you do not have to re-crawl or pay for LLM enrichment, and docs/restore.md documents the procedure. On main, the documented procedure does not work. Both paths fail, for opposite reasons:

$ python manage.py load_recipes dump.json
KeyError: 'title'

$ python manage.py loaddata dump.json
django.db.utils.IntegrityError: Problem installing fixtures:
insert or update on table "recipes_userprofile" violates foreign key constraint
DETAIL:  Key (user_id)=(1) is not present in table "auth_user".

The first fails because dump.json is a Django serialiser fixture (a list of {model, pk, fields}), while load_recipes — and the dump_data command that is supposed to produce the file — speak a different, hand-rolled {recipes, ingredients, meta} shape. The writer and the reader drifted apart and the committed artifact belongs to neither. The second fails because the fixture carries seven UserProfile rows pointing at auth users that were quite rightly not dumped, and Django's model signal creates a profile for every user you make, so pre-creating the users collides on the way back.

This works, from a clean clone:

# 1. Postgres with pgvector, and the extensions the models need
docker compose up -d db
docker compose exec -T db psql -U foodai -d foodai \
  -c "CREATE EXTENSION IF NOT EXISTS vector; CREATE EXTENSION IF NOT EXISTS pg_trgm;"

# 2. Schema
python -m venv .venv && .venv/bin/pip install -r requirements.txt
.venv/bin/python manage.py migrate --noinput

# 3. Placeholder auth users for the ids the fixture references,
#    then drop the profiles the post_save signal just created
.venv/bin/python manage.py shell -c "
from django.contrib.auth.models import User
from recipes.models import UserProfile
for i in (1,2,3,4,5,6,8):
    User.objects.get_or_create(id=i, defaults={'username': f'seed-user-{i}', 'is_active': False})
UserProfile.objects.all().delete()"

# 4. Now the fixture loads: 3,849 objects
.venv/bin/python manage.py loaddata dump.json

# 5. Explicit pks left the sequences behind the data
.venv/bin/python manage.py sqlsequencereset auth recipes > /tmp/seq.sql
docker compose exec -T db psql -q -U foodai -d foodai < /tmp/seq.sql

# 6. Merge the duplicate ingredient rows
.venv/bin/python manage.py canonicalize_ingredients

# 7. Knowledge base, no API key required
.venv/bin/python manage.py generate_llm_wiki

# 8. Placeholder tiles, since media/ is not in the repo
.venv/bin/python manage.py generate_placeholder_images

That yields 841 recipes with calories and structured ingredients, 849 encyclopedia entries with prices, 1,093 ingredient rows, and a 1,761-file wiki. Skip step 5 and the first user you create dies on duplicate key value violates unique constraint "auth_user_pkey", which is a confusing error to meet ten minutes into a project. Steps 6 and 8 are new; the whole sequence is now in restore.md, because a restore procedure nobody has executed is a wish, not a procedure.

What no amount of code fixes is the pictures. 743 of the 841 recipes reference a file under media/recipes/; media/ is gitignored, so all 743 are missing on a fresh clone, and image_url is empty on all 841 rows — the scraper downloaded the images and never kept the URL it fetched them from. So download_images has nothing to download from, and the only recovery path is asking the source site again for URLs the database used to know. The loader now keeps the URL so the loss stops repeating, and the placeholders make the gap visible instead of broken, but the photographs themselves are a crawl I am not entitled to run casually: that site's robots.txt disallows ClaudeBot, Claude-Web and anthropic-ai outright. Its own RecipeBot is welcome, and that is the project owner's decision to make, not the agent's.

Key Takeaways

  1. The _Avoid_ list is the highest-value line in a glossary. Defining a term stops half the drift; naming the words that must not be used for it stops the other half, which is an agent inventing a defensible parallel model for a concept you already have.
  2. Keep the rejected options in the ADR. The smallest diff and the correct design are usually different, and the record of why the cheap option loses is what prevents the next agent — or the next you — from re-choosing it.
  3. Plan serially, execute in parallel, never auto-merge. Bias the planner heavily toward "blocked": two agents on the same model produce two migrations with one parent, and that costs more human attention than another iteration would.
  4. Deterministic branch names make a loop resumable. sandcastle/issue-{id} means re-planning is idempotent, so a crashed iteration continues instead of forking a second attempt.
  5. An agent harness is infrastructure, not a prompt. Nine commits in one day went to sudo, mount, UID/GID and Postgres startup before any agent did useful work. Budget for a Docker image, not a config file.
  6. Verify the spec layer exists. Every prompt told every agent to read AGENTS.md, which has never been in the repository, and the standards file that does exist mandates Vue for a React frontend. A missing instruction file reads as an empty one, and nothing errors.
  7. A generated knowledge base beats embeddings when the queries are predicates. 1,761 files in 1.1 s with zero API calls, rebuildable by deleting the directory. Just know that a per-query full-corpus YAML scan is the price, and build the index before the corpus grows.
  8. Unit heuristics are where domain arithmetic goes to die. "A piece weighs 80 g" is right for eggs, off by 26× for a vanilla pod, and off by four orders of magnitude for a saffron pistil. It is wrong on 1.1% of recipes, always upward, which is exactly the frequency at which nobody notices.
  9. Substring matching over a scraped namespace is a coin flip. 543 of 1,181 ingredient names match more than one price row, one pair spanning €2 to €15,000 per kilo, resolved by dict order. Canonicalise names at ingest, or match exactly and log the misses.
  10. Do not let a default masquerade as a measurement. Zero of 841 recipes have a real shelf life, yet every wiki file states one, and a typed query filters on it. Null forces a question; a plausible default answers it wrongly and confidently.
  11. Never hardcode a date in a test that hits a relative window. 703 tests, one failure, green on the day it merged and rotten since 1 July. Agent review checks the diff against the ticket, and CI checks today — neither can see a fuse.
  12. Spec-driven process makes the code match the spec; it cannot make the spec match the world. Thirty reviewed pull requests, 703 tests and a glossary, and the thing that found a €4,500 plate of fried rice was running the app and reading the output.
  13. A software factory still needs someone to open the box. Not to read the diff — I never did — but to use the product and check its numbers against reality. Every defect here was visible in one afternoon of clicking, and invisible to every layer that only ever compared code against a ticket. Whatever you automate, keep that afternoon.
  14. Fix the layer the bug lives in, not the symptom above it. The savoury-quiche breakfast tempted me into an exclusion list, and the exclusion list immediately served fried chickpea fritters because 'pane' is inside "Panelle". The fix was to stop asking the title and start asking the category. If your patch is another keyword, you are still playing the game that produced the bug.
  15. Run the thing, then run the thing that produces the thing. The crawler had never started from a clean clone — a missing scrapy.cfg, then a pipeline class that was never written, then pagination selectors three months stale, which is why 841 recipes looked like a catalogue and was actually one page per category. Every one of those was invisible to tests, to review and to CI, and obvious within a minute of typing the command.
  16. An unpinned dependency in CI is a clock, not a check. The pipeline was green in June and red in September with nobody touching it: the agent framework moved past a pin CI ignored, and the linter's defaults widened under it. If the build installs a package list nobody wrote down, it is measuring the date.
  17. A stand-in value must be distinguishable from the real thing. My own placeholder images were stored in the same field as photographs and silently taught the crawler that every recipe already had one. I wrote that bug into a codebase while documenting the same shape of bug in it.
